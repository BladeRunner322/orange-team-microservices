# ADR-017: Alerting (Alertmanager + Telegram)

## Контекст

После закрытия Level B в проекте есть полный стек наблюдаемости: Prometheus собирает метрики, Loki + Promtail — логи, Grafana — визуализация. Но всё это **pull-модель**: чтобы увидеть проблему, надо самому зайти и посмотреть.

Триггеры, которые привели к этому ADR:

- **ADR-014** явно фиксирует: «алертинг на "бэкап не появился > 36 ч" запланирован». Без метрики от `backup-db.sh` этот алерт не сделать, но канал доставки нужен заранее.
- **ADR-012** фиксирует: smoke-тесты в CD проверяют только момент деплоя. Если сервис упал через час — workflow зелёный, а прод сломан.
- **ADR-007 (O-1)** в observability перечисляет alerting как задачу.

Никто не смотрит дашборды Grafana 24/7. Solo-проект — тем более. Нужен активный канал уведомлений.

## Решение

### Компоненты

- **Alertmanager** — принимает алерты от Prometheus, группирует, маршрутизирует, отправляет получателям.
- **Prometheus `rule_files`** — правила алертов в `alerts.yml` в корне репо.
- **Telegram** — канал доставки.

### Почему Alertmanager, а не Grafana Alerting

- **Стандартная связка с Prometheus.** Alertmanager — официальный компонент экосистемы, документация и примеры совпадают с нашим стеком.
- **Меньше конфигурации.** Правила в PromQL-файлах (`alerts.yml`), а не в UI Grafana. Всё в git, всё диффится в PR.
- **Silences и grouping из коробки.** Если упадёт несколько сервисов одновременно — придёт одно уведомление, а не 10.
- **Не привязывает алертинг к Grafana.** Grafana может упасть, алертинг продолжит работать.

### Почему Telegram, а не email/Slack

- **Email:** нужен SMTP-сервер (Gmail/Яндекс требуют «пароль приложения»), письма медленнее, спам-фильтры, сложнее настройка.
- **Slack/Discord:** нужен workspace/сервер. Для solo-проекта избыточно.
- **Telegram:** бесплатно, моментально, push на телефон, простой Bot API, не требует доп. сервисов. Оптимально для solo-проекта.

### Что алертим на этом этапе

Три базовых алерта:

| Алерт | Условие | Severity | Окно |
|---|---|---|---|
| `ServiceDown` | `up == 0` для auth/gateway/profiles/exercises | critical | 2m |
| `HighHTTPErrorRate` | доля 5xx Gateway > 5% | warning | 5m |
| `HighGRPCErrorRate` | доля не-OK gRPC > 5% по сервису | warning | 5m |

**Отложено до следующих сессий:**

- CPU/RAM/диск — нужен `node-exporter` (сессия 2).
- «Бэкап не появился > 36 ч» — нужна метрика от `backup-db.sh` через `textfile` collector (сессия 3).
- Алерт на `/ready` — Gateway healthcheck использует `/health`, `/ready` регулярно не опрашивается. Нужен отдельный механизм.

### Секреты

- **`TELEGRAM_BOT_TOKEN`** — секрет, шифруется через SOPS (`pkg`-конвенция ADR-006).
- **`TELEGRAM_CHAT_ID`** — не секрет, но тоже в `.env.enc` для единообразия.
- **`ALERTMANAGER_PORT`** — порт на хосте, открытые значения.
- Токен и chat_id подставляются в `alertmanager.yml` через переменные окружения (Alertmanager поддерживает `${VAR}` в конфиге).
- `alertmanager.yml` монтируется в контейнер только для чтения.

## Последствия

**Плюсы:**

- О падении сервиса узнаёшь сразу, а не от пользователей.
- Все правила алертов — в git, диффятся, ревьюятся.
- Alertmanager группирует уведомления: падение четырёх сервисов = одно сообщение, а не четыре.
- `send_resolved: true` — сообщение «🟢 resolved», когда проблема ушла.

**Минусы:**

- Ещё один контейнер (17 вместо 16). ~30 МБ RAM в простое.
- Ещё один секрет — токен бота. Ротация через SOPS-перешифровку.
- Telegram — внешний сервис. Если он упадёт — алерты не дойдут. Обходного канала нет.
- Правила алертов надо периодически ревизовать: слишком шумные — игнорируются, слишком тихие — не срабатывают.

**Когда пересмотреть:**

- Если алертов станет много и они будут мешать — разделить маршрутизацию по severity (critical → личка, warning → отдельный чат).
- Если появится дежурный / команда — добавить второй канал (SMS, PagerDuty).
- Если Telegram упадёт критично — добавить резервный канал доставки.
- Если правила станут сложными (dependency-алерты, inhibition) — пересмотреть структуру `alertmanager.yml`.
