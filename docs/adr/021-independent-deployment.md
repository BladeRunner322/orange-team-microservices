# ADR-021: Независимый деплой сервисов

## Контекст

По [ADR-019](019-microservices-evolution.md) проект классифицирован как **pre-microservices** — структура правильная (Database per Service, bounded contexts, sync gRPC), но операционные свойства настоящих микросервисов не закрыты. Самое заметное — **атомарный деплой**.

Сейчас CD при **любом** push в `main`:

1. Собирает **все четыре** образа (Auth, Gateway, Profiles, Exercises). Даже если изменился только `Taskfile.yml` — matrix прогоняет все четыре.
2. Пушит все четыре в GHCR с тегами `:latest` и `:<git-sha>`. Откатить один сервис невозможно без отката всего стека.
3. На сервере выполняет `docker compose up -d --no-build --force-recreate` — **пересоздаёт все 19 контейнеров**, включая Caddy, Prometheus, Loki, Alertmanager, все три PostgreSQL и оба Redis.

Это приводит к трём проблемам:

**1. Медленный деплой.** Любое изменение в `services/profiles/**` требует сборки и Auth, и Gateway, и Exercises. При изменении только `infra/prometheus.yml` — тоже все четыре образа собираются.

**2. Downtime всего стека.** `--force-recreate` рвёт соединения ко всем контейнерам: PostgreSQL, Redis, Gateway, Caddy. Даунтайм ~10 секунд на весь стек, даже если менялся только Prometheus.

**3. Нет отката одного сервиса.** Все образы под одним тегом `:latest` + `:<git-sha>`. Если в новом релизе сломан только Profiles — откатывать надо всё, включая Gateway и Auth, которые не менялись.

Дополнительно: инфраструктура (Caddy, Prometheus, Loki, Grafana) пересоздаётся на каждом деплое приложения, хотя её редко надо трогать. Это засоряет уведомления, путает метрики, усложняет отладку.

Это ADR фиксирует **Уровень 1** из ADR-019 — независимый деплой.

## Решение

Четыре независимые подзадачи. Каждая закрывает свой gap.

### 1. CD собирает только изменённые сервисы

В job `changed-services` (использует `tj-actions/changed-files`) добавляются **отдельные outputs** для каждого сервиса:

- `auth_changed` — изменения в `services/auth/**`, `api/auth/**`, `internal/gen/api/auth/**`, `pkg/**`, `go.mod`, `go.sum`.
- `gateway_changed` — изменения в `services/gateway/**`, `api/**`, `internal/gen/api/**`, `pkg/**`, `go.mod`, `go.sum`.
- `profiles_changed` — изменения в `services/profiles/**`, `api/profiles/**`, `internal/gen/api/profiles/**`, `pkg/**`, `go.mod`, `go.sum`.
- `exercises_changed` — изменения в `services/exercises/**`, `api/exercises/**`, `internal/gen/api/exercises/**`, `pkg/**`, `go.mod`, `go.sum`.

**Маппинг proto → сервисы** (пункт 5):

| Изменения в | Пересобираем |
|---|---|
| `api/auth/**`, `internal/gen/api/auth/**` | Auth + Gateway |
| `api/profiles/**`, `internal/gen/api/profiles/**` | Profiles + Gateway |
| `api/exercises/**`, `internal/gen/api/exercises/**` | Exercises + Gateway |

Gateway — потребитель всех proto, поэтому попадает в список при изменении любого из них.

**Матрица `build-and-push` фильтруется** по этим outputs: `matrix.service` содержит только те сервисы, у которых `*_changed == 'true'`. Если ничего не изменилось — job пропускается.

**Отдельный флаг `pkg_changed`**: при изменениях в `pkg/**` пересобираются все четыре сервиса. Это осознанный компромисс — `pkg/**` действительно влияет на всех, а статический анализ импортов (какой пакет какие сервисы затрагивает) сложнее, чем выгода.

### 2. Версионирование образов — semver через git tag

Образы получают **три тега** вместо двух:

- `:<git-sha>` — точная привязка к коммиту. Для отката всегда доступен.
- `:vX.Y.Z` — semver-версия. Появляется **только** когда текущий коммит помечен тегом `v*`. Для остальных пушей в `main` этого тега нет.
- `:latest` — текущий прод. Обновляется **всегда**, и для обычных пушей, и для релизов. Указывает на последний задеплоенный образ.

**Зачем это нужно.** `:<sha>` даёт точный откат, но не подсказывает, какая версия была до бага, в каком sha добавили Circuit Breaker, чем отличается «сейчас» от «неделю назад». Semver-тег превращает откат из «найти sha в GitHub» в «переключить на `:v0.1.0`».

**Формат тега:** `vX.Y.Z` — с префиксом `v`, классический семвер:

- `v0.1.0` — первый релиз.
- `v0.1.1` — patch (баг-фиксы).
- `v0.2.0` — minor (новые фичи, обратно совместимо).
- `v1.0.0` — major (breaking changes).

**Как выпускается релиз.** Ты сам решаешь, когда ставить версию. Обычные пуши в `main` работают как раньше (`:latest` + `:<sha>`). Тег — это **осознанный акт** «вот это мы объявляем релизом»:

```bash
git tag v0.1.0
git push origin v0.1.0
```

**Что происходит при пуше тега.**

1. CD срабатывает на триггер `on: push: tags: ['v*']`.
2. `changed-services` форсирует `any_changed=true` — tag push не смотрит на diff, это релиз.
3. `build-and-push` собирает **все четыре** сервиса (не важно, что менялось — релиз общий).
4. Каждый образ получает три тега: `:latest`, `:<sha>`, `:v0.1.0`.

**Что происходит при обычном пуше в `main`.**

1. CD срабатывает на `on: push: branches: [ main ]`.
2. `changed-services` работает как раньше — детектит изменённые файлы.
3. `build-and-push` собирает (пока) все четыре сервиса.
4. Каждый образ получает два тега: `:latest`, `:<sha>`. Semver-тега нет.

**Первая версия — `v0.1.0`.** Проект в стадии pre-microservices (ADR-019), закрыты Level B и C, Уровень 1 в работе. До `v1.0.0` ещё далеко — это точка «все 7 сервисов реализованы, готово к реальным пользователям».

**Откат одного сервиса** (ручной):

```bash
docker pull ghcr.io/.../profiles:v0.1.0
docker tag  ghcr.io/.../profiles:v0.1.0 ghcr.io/.../profiles:latest
docker compose up -d --no-deps profiles
```

Пока ручной. Автоматизация отката — отдельная задача (Level 2 в ADR-012, триггер — дежурный или SLA).

**Что НЕ делаем.**

- **Автоматический инкремент версии.** Не используем `semantic-release` / conventional commits. Для solo-проекта это оверкилл: жёсткая дисциплина коммитов ради экономии 1 команды раз в 1–2 недели.
- **Per-service версионирование.** Один тег на весь репозиторий, версия общая для всех сервисов. Для монорепо с 4 сервисами — оправданно. Если сервисов станет 10+ с независимыми релизными циклами — пересмотреть.
- **Автоматический откат по тегу.** Откат — ручной.
- **Теги на каждый коммит.** Тег = релиз. Обычные коммиты живут под `:<sha>`.

### 3. CD деплоит только изменённые сервисы

Deploy job вместо `docker compose up -d --no-build --force-recreate` (все 19 контейнеров) выполняет **точечное пересоздание** изменённых:

```bash
# Если изменился auth — пересоздать auth.
docker compose up -d --no-build --no-deps auth
```

`--no-deps` — не пересоздавать зависимости. Если менялся Auth, Profiles перезапускать не надо.

**Что делать с инфраструктурой (пункт 3):** при изменении `infra/**` — `--force-recreate` **всех инфра-контейнеров** (Caddy, Prometheus, Alertmanager, Loki, Promtail, Grafana, node-exporter, WARP). Их 8, они stateless (volumes сохраняются, но пересоздание контейнера данные не теряет). Проще, чем вычислять, что именно затронуто.

**Что делать с миграциями:** если изменился `services/<svc>/migrations/**` — пересоздать `migrate-<svc>` (migrate-контейнеры одноразовые, `restart: "no"`) и сервис `<svc>`:

```bash
docker compose run --rm migrate-auth
docker compose up -d --no-build --no-deps auth
```

Иначе сервис останется на старой схеме БД.

**Итоговый алгоритм deploy job:**

1. `git pull` на сервере.
2. `docker compose pull <list_of_changed_services>` — скачать только нужные образы.
3. Для каждого изменённого сервиса: если менялись миграции — прогнать `migrate-<svc>`, потом `up -d --no-deps <svc>`.
4. Если изменился `infra/**` — `up -d --force-recreate <infra_services>`.
5. `docker image prune -f`.

### 4. Разделение инфраструктуры и приложения (пункт 2)

Единый `infra/docker-compose.yml` разделяется на два файла:

- **`infra/compose.app.yml`** — 4 сервиса + 3 PostgreSQL + 2 Redis + 3 migrate-контейнера.
- **`infra/compose.infra.yml`** — Caddy, Prometheus, Alertmanager, Loki, Promtail, Grafana, node-exporter, WARP.

**Оба файла в одной docker-сети** — либо через общий `networks:` с явным именем, либо через `COMPOSE_FILE=infra/compose.app.yml:infra/compose.infra.yml` (docker compose поддерживает список файлов через двоеточие).

**Критично — имя проекта.** В каждом файле явно задано:

```yaml
name: orange-team-microservices
```

Иначе Compose определяет имя по имени директории — `infra` — и volumes теряются. Volumes объявляются в том файле, к которому относятся: `pgdata-*` и `redisdata-*` в app, `prometheus_data`, `loki_data` и остальные в infra.

**Что это даёт:** деплой приложения работает только с `compose.app.yml` — инфраструктура не тронута. Изменение `infra/prometheus.yml` пересоздаёт только Prometheus, не трогая 4 сервиса.

**CD** использует `COMPOSE_FILE=infra/compose.app.yml:infra/compose.infra.yml` — оба сразу, чтобы не сломать обратную совместимость. Но `up -d --no-deps <service>` всё равно трогает только конкретный сервис.

**Taskfile** получает отдельные таргеты:
- `task app-up` — только приложение.
- `task infra-up` — только инфраструктура.
- `task docker-up` — оба сразу (обратная совместимость).

## Последствия

**Плюсы:**

- **Ускорение деплоя.** При изменении одного сервиса собирается и деплоится только он. Изменение в `infra/**` не трогает приложение.
- **Downtime только конкретного сервиса.** Пересоздание Auth не рвёт соединения Gateway → Profiles и не перезапускает PostgreSQL.
- **Откат одного сервиса.** Тег `:vX.Y.Z` позволяет откатить один сервис без отката всего стека.
- **Инфраструктура перестаёт быть частью релиза приложения.** Prometheus / Loki / Caddy можно обновлять отдельно.
- **Соответствие Уровню 1 ADR-019.** Закрывает главное отличие «микросервисов по названию» от настоящих.

**Минусы:**

- **CD workflow усложняется.** Больше outputs, условий, шагов. Легче запутаться при отладке.
- **Два compose-файла — риск потери volumes.** Если имя проекта `orange-team-microservices` не задано в обоих — Compose создаст новые пустые volumes. Это зафиксировано в ADR и проверено вручную.
- **Semver через `git tag` требует дисциплины.** Если теги не ставить — версионирования нет, только `:<sha>`.
- **Ручной откат.** Автоматического rollback нет — по-прежнему Level 1 из ADR-012.

**Когда пересмотреть:**

- **При появлении второго разработчика.** Правила версионирования и релизов станут обязательными, ручной `git tag` — узким местом. Возможно, переход на `gh release` + conventional commits.
- **При переходе на несколько хостов.** `--no-deps` не работает между хостами — нужна оркестрация (k8s, Nomad).
- **При появлении SLA.** Downtime даже одного сервиса (5–10 секунд) может стать неприемлемым → blue-green или rolling.
- **Если `pkg/**` начнёт меняться часто.** Статический анализ импортов (какой сервис реально зависит от каких пакетов) может стать оправданным.
- **Если сервисов станет больше 7–8.** Явный маппинг «что меняется → что пересобирать» станет громоздким. Возможно, стоит переехать на `bazel` или `nix` с настоящим графом зависимостей.

## Что НЕ делаем в этом PR

- **Автоматический откат.** Level 1 из ADR-012 — detection без rollback. Триггер для Level 2 — дежурный или SLA.
- **Blue-green / canary.** Требует 2× ресурсов и балансировки.
- **Отдельные хосты / k8s.** Оверкилл для одного VDS.
- **Статический анализ импортов.** `pkg/**` → все четыре сервиса. Компромисс, обоснован выше.
- **Отдельный compose на каждый сервис.** Избыточно для 4 сервисов.

## План внедрения

Разбит на четыре сессии:

1. **Разделение compose** (пункт 4) — самая изолированная часть, делается первой.
2. **Semver через `git tag`** (пункт 3).
3. **CD собирает только изменённое** (пункт 1).
4. **CD деплоит только изменённое** (пункт 2).

Каждая — отдельный коммит в ветке `feat/independent-deploy`. При желании — отдельные PR.
