# ADR-024: Асинхронное взаимодействие через Kafka и сервис Notification

## Контекст

Проект построен на синхронном gRPC между сервисами (ADR-004). Все операции — запрос-ответ, ответ нужен сразу. Event bus осознанно не использовался.

Однако есть класс задач, где синхронный вызов — не оптимальный выбор:

**1. Уведомления.** Пользователь выполнил привычку → надо отправить поздравление в Telegram. Если Habits зовёт Notification синхронно, Habits зависит от Notification. Notification упал → Habits падает. Плохо: уведомление не критично для бизнес-операции.

**2. Fan-out.** Событие `user.registered` интересно нескольким сервисам: Profiles (создать пустой профиль), Notification (welcome-сообщение), Analytics (статистика). Синхронно Auth пришлось бы звать каждого и ждать.

**3. Устойчивость к падению downstream.** Если Notification лежит 10 минут — события не должны теряться. Они должны накопиться и обработаться, когда Notification вернётся.

Это **первый кейс в проекте**, где асинхронность даёт реальную пользу, а не является преждевременной оптимизацией.

## Решение

### 1. Kafka как event bus

**Брокер:** Apache Kafka, режим KRaft (без Zookeeper — проще, официальный путь для новых установок).

**Размещение:** отдельный контейнер в `infra/compose.infra.yml`. Single broker — для одного VPS и текущего объёма событий этого достаточно.

**UI:** Kafka UI рядом для отладки — просмотр топиков, consumer groups, lag.

**Нарушение ADR-004.** ADR-004 фиксировал «event bus не используем, только sync gRPC». Это решение **изменяется**: Kafka вводится, но **не отменяет** sync gRPC для существующих вызовов. Оба паттерна живут параллельно:
- Sync gRPC — когда нужен немедленный ответ (GetProfile, ValidateToken, GetExercise).
- Async Kafka — когда ответ не нужен, а нужна гарантия доставки (уведомления, проекции).

### 2. Топики

**Один топик на сервис-издатель.** Внутри — разные события по полю `type`.

- `auth.events` — от Auth.
- `habits.events` — от Habits.

Не один топик на событие. Меньше топиков, проще управлять. Стандартный подход: сервис публикует всё в свой топик, потребители фильтруют по `type`.

### 3. Формат событий

**JSON.** Причины:
- Просто отлаживать (видно глазами).
- Не нужен Schema Registry на старте.
- Легко читать из разных языков (если понадобится).
- Proto для Kafka можно добавить позже, если появится требование строгой схемы.

**Общая структура события:**

```json
{
  "type": "habit.completed",
  "occurred_at": "2026-10-15T12:00:00Z",
  "data": { ... }
}
```

Поля:
- `type` — тип события (строка в формате `<entity>.<action>`).
- `occurred_at` — когда событие произошло (RFC3339, UTC).
- `data` — полезная нагрузка, зависит от типа.

### 4. Что публикуем в первой итерации

Два события:

**`user.registered`** (публикует Auth):
```json
{
  "type": "user.registered",
  "occurred_at": "2026-10-15T12:00:00Z",
  "data": {
    "user_id": "uuid",
    "email": "user@example.com",
    "full_name": "John Doe"
  }
}
```

**`habit.completed`** (публикует Habits):
```json
{
  "type": "habit.completed",
  "occurred_at": "2026-10-15T12:00:00Z",
  "data": {
    "habit_id": "uuid",
    "user_id": "uuid",
    "habit_name": "Пить воду",
    "date": "2026-10-15",
    "streak": 7
  }
}
```

Больше событий — по мере появления реальных потребителей. Не плодим события «на будущее».

### 5. Сервис Notification

**Назначение:** слушает Kafka, отправляет уведомления в Telegram. В MVP — **только админу** (владельцу проекта).

**Почему только админу.** Привязка `user_id ↔ telegram_chat_id` — отдельная большая задача: настройки профиля, oauth-флоу в Telegram, хранение chat_id, отписка. Она не про Kafka. Для изучения event-driven достаточно MVP: событие → сообщение → админский чат.

Привязка пользователей к боту — отдельный ADR, когда появится требование.

**Отдельный бот от Alertmanager.** Нельзя использовать существующий алерт-бот:

- Разные аудитории: Alertmanager — ops (инфраструктурные алерты), Notification — продуктовые события.
- Разные permissions: алерт-бот пишет только админу в один чат. Notification — потенциально многим пользователям (когда появится привязка).
- Разные секреты: утечка одного токена не компрометирует другой функционал.

Регистрируется **новый бот** у @BotFather. Токен и chat_id — в `.env.enc`, отдельные от `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID` (которые для алертов).

### 6. Идемпотентность

**Kafka даёт at-least-once delivery.** Одно событие может прийти потребителю дважды: при ребалансировке consumer group, при retry после ошибки. Без защиты пользователь получит два поздравления.

**Решение:** таблица `notification.processed_events`.

```sql
CREATE TABLE notification.processed_events (
    event_id     UUID PRIMARY KEY,
    processed_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

**Логика:**
1. Consumer получает событие с `event_id`.
2. `INSERT INTO processed_events (event_id) VALUES ($1) ON CONFLICT DO NOTHING`.
3. Если `RowsAffected == 0` — событие уже обработано, пропускаем.
4. Иначе — обрабатываем и коммитим offset в Kafka.

**Почему `event_id` в событии.** Каждое событие на стороне издателя получает уникальный `event_id` (UUID). Это часть формата события:

```json
{
  "event_id": "uuid",
  "type": "habit.completed",
  "occurred_at": "...",
  "data": { ... }
}
```

**Порядок операций:**
1. INSERT в `processed_events`.
2. Отправка в Telegram.
3. Commit offset в Kafka.

Если упало между 1 и 2 — при retry событие пропустится (уже в processed), но уведомление не уйдёт. Это потеря, но редкая. Если упало между 2 и 3 — при retry событие пропустится (уже в processed), уведомление не дублируется. Корректно.

### 7. Outbox pattern — не в этой итерации

**Проблема:** Habits сохранил привычку в БД, потом публикует событие в Kafka. Если Kafka недоступна — событие потеряно. БД говорит «привычка создана», Kafka — «события нет».

**Классическое решение** — Outbox: писать событие в таблицу `outbox` **в той же транзакции**, что и бизнес-данные. Фоновый воркер читает outbox и публикует в Kafka. Если Kafka упала — события остаются в outbox, публикуются, когда вернётся.

**Что даёт:** гарантия, что если транзакция прошла — событие точно уйдёт в Kafka.

**Почему не сейчас.** В текущей итерации уведомления не критичны. Потеря `habit.completed` → пользователь не получил поздравление. Не катастрофа.

**Триггер для Outbox:** появление критичного события, где потеря недопустима (например, `payment.processed`, `subscription.renewed`). Тогда — отдельный ADR.

**Что делаем вместо Outbox:** публикуем в Kafka сразу после успешной транзакции в БД. Если Kafka недоступна — логируем ошибку, но не откатываем бизнес-операцию.

### 8. Метрики и алерты

**Метрики в Notification:**
- `kafka_consumer_lag` — насколько отстаёт от последнего offset.
- `kafka_events_processed_total{type, result}` — сколько событий обработано (`result: success|failed|skipped`).
- `kafka_events_failed_total{type}` — сколько упало.

**Метрики в издателях (Auth, Habits):**
- `kafka_events_published_total{topic, type, result}` — сколько опубликовано.

**Алерты (в `infra/alerts.yml`):**
- `KafkaConsumerLagHigh` — lag > 1000 событий в течение 5 минут → warning.
- `KafkaProducerErrors` — ошибок публикации > 1% за 5 минут → warning.

### 9. Порты и размещение

**Notification-сервис:**
- gRPC — не нужен. Notification только читает Kafka, никто его не зовёт.
- HTTP (health/ready/metrics) — **8085** (Docker) / **8095** (локально).
- PostgreSQL — `notification_db` на хосте **5436**.
- Kafka — контейнер в `compose.infra.yml`, порт **9092** внутри сети.

**Postgres — почему нужен.** Таблица `processed_events` для идемпотентности. Без неё нельзя.

1. **ADR-024** — этот документ.

4. **Domain + usecases в Notification** — обработка событий.
5. **Consumer в Notification** — чтение из Kafka.
6. **Publisher в Auth** — `user.registered`.
7. **Publisher в Habits** — `habit.completed`.

## Последствия

**Плюсы:**

- Habits и Auth не зависят от Notification. Notification упал — публикация продолжается, события накопятся в Kafka.
- Fan-out становится тривиальным. Добавить третьего потребителя `user.registered` — просто новый consumer group, ничего не меняем в Auth.
- Устойчивость к падению downstream.
- Опыт работы с Kafka, consumer groups, offsets, идемпотентностью.

**Минусы:**

- Новая инфраструктура: ~200–300 МБ RAM, ещё один контейнер.
- Сложнее отладка: событие может быть потеряно между БД и Kafka (без Outbox).
- Kafka — оверкилл для текущих объёмов. Уведомления можно было бы отправлять синхронно из Habits в Notification. Kafka выигрывает только при падении Notification и при росте числа потребителей.
- Дублирование инфраструктуры: Kafka + Postgres для Notification. Для отправки Telegram-сообщения.

**Когда пересмотреть:**

- Если событий станет мало и Kafka не оправдывает RAM — вернуться к sync вызову.
- Если понадобится строгая гарантия доставки — добавить Outbox.
- Если появится fan-out с 3+ потребителями — оценить Schema Registry для строгой схемы событий.
- Если событий станет очень много — партиционирование, реплики брокера.
