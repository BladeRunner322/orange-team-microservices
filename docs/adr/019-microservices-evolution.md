# ADR-019: Эволюция в сторону микросервисов

## Контекст

Проект с самого начала позиционировался как микросервисы: четыре сервиса (Auth, Gateway, Profiles, Exercises), у каждого своя БД (ADR-004), независимые домены, свой процесс в docker-compose. Это правильный фундамент.

Однако при аудите выяснилось, что по ряду ключевых признаков система ближе к **распределённому монолиту**, чем к «настоящим» микросервисам. Точнее — к промежуточной стадии, которую можно назвать **pre-microservices**: структура правильная, операционные свойства — нет.

### Что уже сделано правильно

- **Database per Service** — у каждого сервиса своя БД, cross-service FK нет (ADR-004).
- **Bounded contexts** — границы проведены по бизнесу, не по таблицам.
- **Независимые модели** — User в Auth, Profile в Profiles, Exercise в Exercises. Общих доменных моделей нет.
- **Общий `pkg/`** — только инфраструктура (logger, metrics, postgres, grpc, health). Бизнес-логика не шарится.
- **Осознанные архитектурные решения** — sync gRPC, отсутствие event bus, отказ от саг зафиксированы в ADR-004 и ADR-003.

### Что не так с точки зрения «настоящих» микросервисов

**1. Атомарный деплой.** CD пересобирает и пересоздаёт **все** 19 контейнеров на каждый push. Изменение в одном сервисе (или даже только в `Taskfile.yml`) приводит к пересозданию всего стека, включая Caddy, Prometheus, Loki.

**2. Отсутствие failure isolation.** Только sync gRPC. Если Profiles тормозит — Gateway копит запросы и падает сам. Circuit Breaker, Retry, bulkheads не реализованы.

**3. Только синхронная коммуникация.** Event bus, outbox, saga не используются. Если downstream недоступен — операция падает, клиент повторяет.

**4. `:latest` для образов.** Версионирование образов по semver отсутствует. Невозможно откатить один сервис, не задев остальные.

**5. Неполная observability.** `request_id` пробрасывается (ADR-007, O-2 закрыт), но distributed tracing (OpenTelemetry) не внедрён.

### Почему это важно сейчас

Проект — учебный/портфолио, но с прицелом на реальную работу. Для собеседований и production-готовности нужны конкретные признаки: независимый деплой, failure isolation, distributed tracing. Без них система остаётся «микросервисы по названию».

## Решение

Зафиксировать roadmap эволюции от текущего состояния к микросервисам. Разбить на уровни с явными приоритетами и триггерами для перехода между уровнями.

### Уровень 1 — Независимый деплой (первый приоритет)

**Цель:** изменение в одном сервисе не приводит к пересозданию остальных.

**Что делаем:**

- **CD собирает только изменённые сервисы.** Сейчас matrix собирает все четыре и пушит в GHCR всегда, независимо от того, что изменилось. Нужно использовать `changed-services` не только для решения «деплоить или нет», но и для **списка конкретных сервисов**.
- **CD деплоит только изменённые сервисы.** Вместо `docker compose up -d --force-recreate` (все) — пересоздание только тех контейнеров, чьи образы обновились.
- **Версионирование образов по semver.** Вместо `:latest` — теги вида `:v1.2.3`. Возможность откатить один сервис без отката всего стека.
- **Разделение инфраструктуры и приложения.** Caddy, Prometheus, Loki, Grafana, Alertmanager, node-exporter — отдельный compose-файл / отдельный деплой. Их рестарт не должен быть частью деплоя сервисов.

**Что НЕ делаем на этом уровне:**

- Не разделяем на отдельные хосты. Один VDS остаётся.
- Не вводим k8s. Оверкилл для масштаба.
- Не делаем blue-green. Даунтайм 5-10 секунд приемлем.

**Триггеры для перехода к уровню 2:**

- Появление второго разработчика → обязательная координация релизов станет проблемой.
- Реальные пользователи с SLA → даунтайм 5-10 секунд при каждом деплое неприемлем.
- Число сервисов > 6 → атомарный деплой станет неподъёмным.

### Уровень 2 — Failure isolation (второй приоритет)

**Цель:** падение одного сервиса не роняет всё.

**Что делаем:**

- **Circuit Breaker на client-стороне.** В `pkg/grpc/client` — интерсептор `CircuitBreakerInterceptor`. Отслеживает долю ошибок к каждому downstream, при превышении порога временно перестаёт слать запросы (fail fast).
- **Retry с exponential backoff.** В `pkg/grpc/client` — `RetryInterceptor`. Только для идемпотентных вызовов (`GetProfile`, `GetExercise`). Не для мутаций (`CreateWorkout` — не ретраить без идемпотентного ключа).
- **Bulkheads.** Ограничение параллельных вызовов к каждому downstream. Реализуется через семафор в интерсепторе.
- **Fallback / degradation.** Для необязательных данных — graceful degradation. Например, если Profiles недоступен, `GET /users/me` может вернуть `profile_completed: false` и 200 вместо 500. Решается по каждому эндпоинту.

**Что НЕ делаем на этом уровне:**

- Не вводим event bus. Сначала изолируем то, что есть.
- Не делаем saga. Она нужна только когда появятся cross-service транзакции.

**Триггеры для перехода к уровню 3:**

- Появление операции, которая пишет в две БД (например, Workouts → Profiles через событие).
- Появление projections, требующих eventual consistency (Leaderboard).
- Обнаружение регулярных каскадных отказов даже с CB (значит, sync — не тот паттерн для конкретной операции).

### Уровень 3 — Асинхронность (третий приоритет)

**Цель:** рассинхрон через события, где sync не подходит.

**Что делаем (только при триггере):**

- **Event bus** — Redis Streams (уже есть в стеке) или NATS JetStream.
- **Outbox pattern** — атомарная запись в БД + событие в шину.
- **Saga** — для критичных операций с несколькими шагами.
- **Eventual consistency** для проекций (`user_workout_score` через событие, а не sync-запрос).

**Что НЕ делаем сейчас:**

- Не вводим заранее. ADR-004 явно зафиксировал отказ от event bus как осознанный выбор.
- Не переписываем существующие sync-вызовы, которые работают хорошо.

**Триггеры для перехода к уровню 4:**

- 7+ сервисов.
- Несколько хостов.
- Потребность в zero-downtime деплое (SLA).
- Команда 3+ разработчиков.

### Уровень 4 — Distributed tracing

**Цель:** полная картина запроса через все сервисы, включая latency breakdown.

**Что делаем:**

- **OpenTelemetry SDK** в каждом сервисе.
- **W3C `traceparent`** вместо (или рядом с) `x-request-id`.
- **Tempo** (или Jaeger) как backend.
- **Grafana datasource** на Tempo.
- **Span-ы** вокруг gRPC-вызовов, HTTP-хендлеров, операций с БД.

**Триггер:** реальная потребность отладки latency (не только error).

### Уровень 5 — Физическое разделение (крайний случай)

**Что делаем (только при реальной необходимости):**

- Несколько хостов или k8s.
- Managed БД (Selectel Managed PostgreSQL).
- Service mesh (Istio, Linkerd) — только если сервисов > 10.

**Триггер:** текущий VDS не тянет нагрузку, или сервисов > 10.

### Что НЕ делаем вообще (по крайней мере, в обозримом будущем)

- **k8s** — оверкилл для одного хоста и 4 сервисов.
- **Service mesh** — оверкилл для 4 сервисов на одном хосте.
- **Kafka** — Redis Streams / NATS легче и достаточно.
- **Микросервис на каждый CRUD** — границы уже правильные.

## Последствия

**Плюсы:**

- Явный план эволюции вместо разрозненных задач.
- Триггеры для перехода между уровнями — не делаем заранее.
- Каждый уровень закрывает конкретную проблему, а не «потому что так надо».
- Система постепенно становится «настоящими микросервисами» без переписывания с нуля.

**Минусы:**

- Уровень 1 требует серьёзной переработки CD. Это самый большой объём работы.
- Уровень 2 (CB + Retry) добавляет сложности в `pkg/grpc/client`.
- Не «настоящие микросервисы» ещё несколько месяцев — это осознанный компромисс.

**Когда пересмотреть:**

- Если «микросервисы ради микросервисов» перестанут быть целью (например, проект останется пет-проектом) — уровни 3-5 можно вообще не делать.
- Если появится реальная нагрузка — пересмотреть порядок приоритетов (например, tracing важнее независимого деплоя).

## Что делаем сначала

**Первый PR после этого ADR:** Circuit Breaker + Retry (Уровень 2). Причина — меньше работы, быстрее даёт видимый эффект, готовит инфраструктуру для независимого деплоя (CB на client-стороне нужен, даже если деплой станет атомарным для одного сервиса).

**Второй PR:** независимый деплой (Уровень 1). Большая работа, отдельный PR.

**Дальше — по триггерам.**
