# ADR-015: HTTPS через Caddy

## Контекст

Сервисы доступны по HTTP на `http://136.234.4.93:8081` (Gateway). Проблемы:

- **Трафик не шифрован.** Логины, пароли, JWT-токены ходят по сети открытым текстом.
- **Нет домена.** Клиент вынужден запоминать IP-адрес.
- **Let's Encrypt не может выдать сертификат на IP.** Только на домен.

Для прода нужен HTTPS и человекочитаемый адрес. Встаёт вопрос: как организовать TLS-терминацию, чем получать и продлевать сертификаты, где хранить ключи.

## Решение

### Провайдер домена: DuckDNS (временно)

Бесплатный поддомен `solevolevingms.duckdns.org` через [duckdns.org](https://www.duckdns.org).

**Почему временно и почему DuckDNS:**

- **Платный домен не критичен на этапе MVP.** Красивый `.ru` добавим позже — переезд занимает 15 минут (одна A-запись, одна строка в `.env`).
- **DuckDNS даёт полноценный поддомен.** Let's Encrypt работает с ним так же, как с платным доменом.
- **A-запись управляется через простой API.** Если IP сервера когда-нибудь изменится, обновить можно одной curl-командой.

**Триггер перехода на платный домен:** публичный запуск, реальные пользователи, потребность в брендированном адресе.

### TLS-терминация: Caddy

Caddy — reverse proxy с автоматическим Let's Encrypt.

**Почему Caddy, а не альтернативы:**

- **Автоматические сертификаты из коробки.** Не нужно ставить certbot, писать cron на `certbot renew`, парсить конфиги nginx.
- **HTTP-challenge без плагинов.** Стандартный образ `caddy:2-alpine` умеет всё, что нужно.
- **Конфиг — 3 строки.** `Caddyfile` читается за 10 секунд.
- **HTTP/2 и HTTP/3 по умолчанию.**
- **Автоматический редирект HTTP → HTTPS.**

**Рассмотренные альтернативы:**

- **Nginx + certbot.** Больше конфигов, cron на продление, ручной перезапуск. Классика, но Caddy проще.
- **Traefik.** Мощнее, но требует labels на каждом контейнере и сложнее конфиг. Оверкилл для 4 сервисов.
- **Cloudflare Tunnel.** Не подходит: TLS-терминация на стороне Cloudflare, зависимость от внешнего вендора.
- **Selectel Load Balancer.** Платно, избыточно для одной ноды.

### Схема

```
Клиент → HTTPS :443 → Caddy (TLS-терминация) → HTTP gateway:8081 (внутри docker-сети)
       → HTTP  :80  → Caddy (redirect)       → HTTPS
```

- Caddy — единственный контейнер с портами 80/443, доступными снаружи.
- Gateway доступен только внутри docker-сети по имени `gateway:8081`.
- Auth/Profiles/Exercises — тоже только внутри сети, снаружи закрыты.

### Способ валидации: HTTP-challenge

Caddy использует **HTTP-01 challenge** Let's Encrypt. Как работает:

1. Caddy просит у Let's Encrypt сертификат для `solevolevingms.duckdns.org`.
2. Let's Encrypt стучится на `http://solevolevingms.duckdns.org/.well-known/acme-challenge/<token>`.
3. Caddy отвечает случайным токеном.
4. Let's Encrypt проверяет токен и выдаёт сертификат.

**Почему HTTP, а не DNS:**

- HTTP-challenge работает со стандартным образом `caddy:2-alpine` — **никаких плагинов**.
- DNS-challenge требует плагин `caddy-dns/duckdns`, встроенный при сборке кастомного образа. Дополнительный Dockerfile, свои релизы, обновления.
- DNS-challenge нужен только если порт 80 недоступен или нужен wildcard-сертификат. У нас порт 80 открыт.

**Следствие:** токен DuckDNS **не нужен** для HTTP-challenge. Оставлен в резерве на случай перехода на DNS-challenge.

### Хранение сертификатов

Caddy хранит сертификаты в volume `caddy_data` (путь `/data` внутри контейнера). При перезапуске контейнера сертификат подхватывается, повторная выдача не требуется.

**Volume сохраняется** при `docker compose down`, удаляется только при `docker compose down -v`.

### Продление

Caddy продлевает сертификат **автоматически**, за 30 дней до истечения. Никаких cron, никаких ручных действий.

**Триггер для пересмотра:** если алертинг (отдельный ADR) начнёт ругаться на «сертификат скоро истекает» — что-то сломалось в Caddy, разбираться.

## Последствия

**Плюсы:**

- HTTPS бесплатно, автоматически, без ручных операций.
- Ноль зависимостей от certbot и cron.
- Конфиг — 3 строки, читается моментально.
- HTTP → HTTPS редирект из коробки.
- Человекочитаемый адрес `solevolevingms.duckdns.org`.

**Минусы:**

- Ещё один контейнер (Caddy) — плюс ~30 МБ RAM в простое.
- DuckDNS — внешний сервис. Если он упадёт (что редкость), домен перестанет резолвиться. При переезде на платный домен — проблема уходит.
- HTTP-challenge требует открытый порт 80. Если однажды закроется (например, хостинг запретит) — придётся переходить на DNS-challenge с плагином.
- Сертификаты Let's Encrypt живут 90 дней и **не подходят для внутренней инфраструктуры** (только для публичных сервисов). У нас публичный только Gateway, поэтому ок.

**Когда пересмотреть:**

- Публичный запуск / реальные пользователи → платный домен `.ru` у аккредитованного регистратора. Переезд 15 минут.
- Порт 80 недоступен → DNS-challenge + плагин `caddy-dns/duckdns`.
- Нужны wildcard-сертификаты (для поддоменов) → тоже DNS-challenge.
- Появится балансировщик / несколько нод → Load Balancer + сертификат на нём.

## Плейсхолдеры

В `.env`:

- `DOMAIN=solevolevingms.duckdns.org` — публичный домен, на который Caddy выпускает сертификат.

Токен DuckDNS **не нужен** при HTTP-challenge. Храним на будущее вне `.env` (в блокноте / password manager).
