# ADR-012: Оптимизация CI/CD

## Контекст

CD-пайплайн (`.github/workflows/ci-cd.yml`) собирает и пушит
Docker-образы для четырёх сервисов (Auth, Gateway, Profiles,
Exercises). Текущая структура:

- `ci` job: unit-тесты + 4 smoke-build через `go build`.
- `cd` job: 4 шага `docker/build-push-action` **последовательно**
  (auth → gateway → profiles → exercises), затем SSH-деплой.
- Все build-push шаги используют условие `any_changed == 'true'`,
  то есть при изменении **любого** сервиса или `pkg/**`
  пересобираются **все четыре** образа.

Замеры последних прогонов:

| Фаза | Время |
|---|---|
| `ci` | 2–4 мин |
| `cd`: 4 × docker build | **4–12 мин** (боттлнек) |
| `cd`: 4 × docker push | 2–4 мин |
| `deploy` (SSH) | 1–2 мин |

Итого деплой: **~10–18 мин** при пуше в `main`. Большая часть
времени уходит на последовательную сборку образов без
переиспользования слоёв.

Две независимые проблемы:

1. **Нет docker layer caching.** Каждый build начинается с
   чистого листа. `Dockerfile` делает `COPY vendor` + `RUN go build` —
   без кеша эти слои пересобираются каждый раз, даже если код
   не менялся.
2. **Сборка последовательная.** 4 сервиса собираются один за
   другим на одном runner'е, хотя они полностью независимы.

## Решение

Две оптимизации, применяются вместе.

### 1. Docker layer caching через GitHub Actions Cache

В каждый шаг `docker/build-push-action` добавляется:

```yaml
cache-from: type=gha
cache-to: type=gha,mode=max
```

**Как работает.** BuildKit сохраняет промежуточные слои в
GitHub Actions Cache (`type=gha` — встроенный бэкенд, не требует
внешнего registry или S3). При следующей сборке:

- Слои, не изменившиеся с прошлого запуска (например,
  `COPY go.mod go.sum` + `RUN go mod download` + `COPY vendor`),
  берутся из кеша — за секунды.
- Пересобираются только слои, где код изменился.
- `mode=max` — кешируются **все** промежуточные слои (не только
  финальный образ), включая build-stage. Это критично для
  multi-stage Dockerfile.

**Ограничения GitHub Actions Cache:**

- Общий лимит 10 ГБ на репозиторий. При превышении старые
  записи вытесняются LRU.
- Кеш живёт 7 дней без обращений.
- Каждый образ Exercises ~150–300 МБ (alpine + бинарник),
  промежуточные слои меньше. 4 сервиса × 2–3 слоя × ~50 МБ —
  вписывается в лимит.

### 2. Matrix strategy для build-push

Текущий `cd` job разбивается на три job'а:

```
ci
 └── changed-services    (определяет any_changed)
      └── build-and-push (matrix: 4 сервиса, параллельно)
           └── deploy    (SSH, один вызов)
```

`build-and-push` использует:

```yaml
strategy:
  fail-fast: false
  matrix:
    service: [auth, gateway, profiles, exercises]
```

**Что даёт:**

- 4 образа собираются **параллельно** на 4 runner'ах →
  фаза build-push занимает `max(t_auth, t_gateway, t_profiles, t_exercises)`
  вместо суммы.
- `fail-fast: false` — если один сервис упал (например, Exercises
  не собирается из-за ошибки в коде), остальные три всё равно
  соберутся и запушнутся. Упавший сервис не блокирует деплой
  тех, кто готов.

**Что требует:**

- `changed-services` выносится в отдельный job (не шаг внутри
  `cd`), потому что outputs между job'ами идут через
  `needs.X.outputs.Y`.
- SSH-деплой становится отдельным job'ом, зависящим от
  `build-and-push`.
- Матрица добавляет 3 job'а вместо 1 (`cd`) — больше YAML,
  больше `needs`-связей, дольше стартап (у каждого job'а свой
  `setup Go` / `checkout`).

**Что НЕ делаем:**

- **CI job не переводим на matrix.** Smoke-build (`go build`) —
  лёгкий, секунды. Setup Go × 4 накладнее, чем экономия.
- **`changed-services` не оптимизируем.** Сейчас любое изменение
  в `pkg/**` пересобирает все сервисы. Это осознанный
  компромисс: `pkg/**` действительно влияет на все сервисы.
  Отдельные `if:` под каждый сервис усложнят workflow без
  значимой выгоды.

## Ожидаемый эффект

| Фаза | Было | Стало (кеш) | Стало (кеш + matrix) |
|---|---|---|---|
| `cd`: 4 build-push | 6–16 мин | 2–6 мин | **1–2 мин** |
| Итого деплой | 10–18 мин | 6–10 мин | **4–6 мин** |

Точные цифры зависят от:

- Первый запуск после внедрения кеша — медленный (кеш пуст).
- Второй и последующие — быстрые (кеш попадает).
- Если менялся только один сервис — быстро (остальные берутся
  из кеша полностью).
- Если менялся `pkg/**` — все 4 сервиса пересобираются, но
  кеш всё равно ускоряет слои ниже `COPY pkg`.

## Smoke-тесты

**Реализовано** (2026-10-08).

После шага `deploy` запускается отдельный job `smoke-test`. Делает три проверки против `https://sololevelingms.duckdns.org`:

1. **`GET /health` → 200 + `status:ok`.** Gateway жив.
2. **`GET /ready` → 200 + `status:ok`.** Gateway, Redis, gRPC-каналы к Auth/Profiles/Exercises живы.
3. **`POST /login` с неверными кредами → 401.** Проверяет всю цепочку: Caddy → Gateway → Auth → PostgreSQL. Если цепочка сломана, вернётся 5xx вместо 401.

Перед проверками job ждёт до 60 секунд (10 попыток с интервалом 6 секунд) — после рестарта контейнеры не сразу готовы принимать трафик.

**Что даёт:**
- Если деплой сломал прод (миграция не применилась, `.env` не подхватился, контейнер упал) — workflow краснеет через ~10 секунд после `docker compose up`. Раньше узнавали утром от пользователей или при следующей ручной проверке.
- Не заменяет integration/E2E — только «дым идёт или нет».

**Что не проверяет:**
- Бизнес-логику (создание тренировки, RBAC, rate limiting).
- Идемпотентность, snapshot, soft delete.
- Регрессии в отдельных эндпоинтах.

Это дело Postman-коллекций и integration-тестов.

## Пересоздание контейнеров при деплое

**Проблема.** `docker compose up -d --no-build` пересоздаёт контейнер только если изменился его манифест в compose (образ, ports, volumes, env) или содержимое `.env`. Изменения **содержимого монтируемых конфиг-файлов** compose не отслеживает — для него это тот же volume, тот же путь.

Сервисы, которые читают конфиг при старте и не перечитывают его автоматически:

- `alertmanager` — `infra/alertmanager.yml`
- `prometheus` — `infra/prometheus.yml`, `infra/alerts.yml`
- `promtail` — `infra/promtail-config.yml`
- `caddy` — `infra/Caddyfile`

Итог: правишь `infra/alerts.yml` в PR, мержишь, CD зелёный, а прод работает на старых правилах. Первый инцидент — узнаешь, что алерт не срабатывает, потому что конфиг не применился.

**Решение.** В deploy job добавлен `--force-recreate`:

```
docker compose up -d --no-build --force-recreate
```

Все контейнеры пересоздаются на каждом деплое, конфиги гарантированно актуальны.

**Что это значит по факту:**

- Postgres и Redis тоже пересоздаются. Данные не теряются (volumes), но соединения рвутся на 2–5 секунд. Клиенты переподключаются автоматически.
- Downtime ~10 секунд на весь стек. Для solo-проекта без SLA — приемлемо.
- CD-джоба теперь занимает на 5–10 секунд больше.

**Альтернатива** — перечислять только сервисы с конфигами:

```
docker compose up -d --no-build --force-recreate alertmanager prometheus promtail caddy
```

Быстрее, но список надо поддерживать вручную при добавлении новых конфиг-сервисов. При первом забытом сервисе — та же проблема с неприменённым конфигом. Отвергнуто в пользу простоты.

**Когда пересмотреть:**

- Появится SLA с пользователями, даунтайм 10 секунд станет недопустимым → blue-green или rolling.
- Стек переедет в k8s → там ConfigMap-изменения триггерят rolling restart автоматически.

**Про `COMPOSE_FILE` и SSH-деплой.** Переменные окружения GitHub Actions не пробрасываются на сервер через `appleboy/ssh-action` — SSH-скрипт выполняется в новой shell-сессии. `COMPOSE_FILE: infra/docker-compose.yml` в глобальном `env:` работает только для команд, запускаемых **на раннере**. В deploy job (SSH на сервер) их надо выставлять явно:

```
export COMPOSE_FILE=infra/docker-compose.yml
export COMPOSE_ENV_FILES=.env
```

Тот же путь и `COMPOSE_ENV_FILES` — потому что Compose ищет top-level `.env` рядом с compose-файлом, а `.env` лежит в корне репозитория.

**Про триггеры changed-services после переноса в infra/.** Изначально в `changed-services` были перечислены семь отдельных путей (`docker-compose.yml`, `Caddyfile`, `prometheus.yml`, `alerts.yml`, `alertmanager.yml`, `loki-config.yml`, `promtail-config.yml`). После переноса в `infra/` эти пути перестали матчиться — коммит с правками `infra/docker-compose.yml` триггерил `any_changed = false`, деплой пропускался.

Решение — заменить семь путей на `infra/**`. При добавлении нового конфига в `infra/` не нужно дописывать его в список.

**Про имя проекта.** Compose определяет имя проекта по имени директории с compose-файлом. Раньше файл был в корне (`orange-team-microservices/docker-compose.yml`) → проект `orange-team-microservices`, все volumes с префиксом `orange-team-microservices_`. После переноса в `infra/` Compose стал бы использовать `infra` как имя проекта → volumes `infra_pgdata-auth` и т. д. То есть **новые пустые volumes** вместо существующих.

Решение — задать имя проекта явно в `infra/docker-compose.yml`:

```yaml
name: orange-team-microservices
```

Это top-level поле Compose (v2.20+). Без него перенос compose-файла в поддиректорию = потеря данных.

## Уведомления о деплое в Telegram

**Задача.** Знать результат деплоя без ручной проверки GitHub Actions — приходит ли уведомление в Telegram при успехе и при провале.

**Решение.** Отдельный job `notify` в конце пайплайна:

- `needs: [ci, changed-services, build-and-push, deploy, smoke-test]` — зависит от всех предыдущих.
- `if: always() && github.event_name == 'push' && github.ref == 'refs/heads/main'` — выполняется всегда, даже если предыдущие упали. Но только на push в main, не на PR.
- Смотрит на `needs.X.result` каждого job'а и формирует одно сообщение: `✅ success`, `❌ failed` (с указанием упавшего job'а) или `⏭️ nothing to deploy`.
- Отправка — прямым `curl` к `api.telegram.org`.

**Почему без WARP.** Job бежит на GitHub-раннере (`ubuntu-latest`), а не на продакшн-сервере. С GitHub-раннера Telegram доступен напрямую — блокировка российских провайдеров там не действует.

**Секреты — через SOPS.** Токен и chat_id не дублируются в GitHub Secrets. В notify-джобе используется:

```
sops --decrypt --input-type dotenv --extract '["TELEGRAM_BOT_TOKEN"]' .env.enc
```

`--extract` вытаскивает одно значение, не создавая `.env` на диске. `SOPS_AGE_KEY` уже в GitHub Secrets — используется в deploy job.

**Альтернатива, отвергнутая:** дублирование `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` в GitHub Secrets. Плюс — простота. Минусы — два источника истины, ротация в двух местах, две точки утечки.

**Когда пересмотреть:**

- Если уведомлений станет много (несколько окружений, отдельные каналы для успеха и ошибок) — разделить маршрутизацию.
- Если понадобится отправлять в разные чаты по severity — отдельный ADR.

## Hot-reload как альтернатива рестарту

Для Alertmanager и Prometheus есть hot-reload без пересоздания контейнера:

- Alertmanager: `POST /-/reload` (флаг `--web.enable-lifecycle` включён в compose).
- Prometheus: `POST /-/reload` (флаг `--web.enable-lifecycle` не включён, отдельная задача).

Taskfile таргеты: `task alertmanager-reload`.

Это не заменяет `--force-recreate` в CD (не все сервисы умеют reload), но удобно для локальной работы: правишь `infra/alertmanager.yml` — `task alertmanager-reload` — проверяешь без рестарта.

## Rollback: стратегия

**Решение (2026-10-08): Level 1 — post-deploy detection без auto-rollback.**

Что это значит:
- Smoke-тесты **обнаруживают** сломанный деплой (workflow краснеет).
- Прод **остаётся сломанным** — никакого автоматического отката нет.
- Владелец проекта (вручную) заходит на сервер, смотрит логи, откатывает или чинит.

**Почему так, а не иначе:**

| Уровень | Что делает | Стоимость | Когда имеет смысл |
|---|---|---|---|
| **Level 1** (наш) | Smoke → красный workflow → ручной разбор | 30 мин | Solo, MVP, нет SLA |
| **Level 2** | Smoke упал → авто-откат на предыдущий `<git-sha>` | +1–2 ч | Появился дежурный / SLA |
| **Level 3** | Blue-green / canary | Дни | Несколько нод, k8s |

Для текущего масштаба (solo, один VPS, нет дежурного) Level 1 даёт 80% пользы за 10% усилий. Красный workflow в момент провала — уже огромный шаг вперёд: раньше не было вообще никакой проверки.

**Триггеры для перехода на Level 2:**
- Появится дежурный / команда → нужен rollback без человека.
- SLA с клиентами → прод не должен лежать дольше N минут.
- Инцидент, который был больно откатывать вручную → наступаем на грабли, вводим автоматизацию.

**Что НЕ делаем сейчас:**
- Не пишем auto-rollback в workflow. Дороже, чем польза.
- Не делаем blue-green. Требует 2× ресурсов и балансировки.
- Не вводим канареечные деплои. Не для одного сервера.

**Практический флоу при провале smoke:**

1. Красный workflow → уведомление от GitHub Actions.
2. Смотрим лог smoke-шага — какой именно `curl` упал.
3. Идём на сервер: `docker ps`, `docker logs <service> --tail 50`.
4. Чиним (или откатываем на предыдущий `:<sha>` вручную).
5. Пушим фикс — CD прогоняет деплой снова.

## Последствия

**Плюсы:**

- Деплой ускоряется в 2–4 раза (типично), в отдельных случаях — в 5+.
- Ошибка в одном сервисе не блокирует деплой остальных
  (`fail-fast: false`).
- Добавление нового сервиса в матрицу — одна строка в
  `matrix.service`. Больше не нужно копипастить весь
  build-push блок.
- Docker кеш работает и в CI (если позже добавим сборку образа
  на PR для проверки).

**Минусы:**

- Workflow усложняется: 4 job'а вместо 2, между ними явные
  `needs`.
- Matrix добавляет время на orchestration: 4 runner'а
  запускаются параллельно, но каждый делает свой
  `setup Go` / `checkout` / `login to GHCR`. Накладные ~20–40
  секунд на старте.
- GitHub Actions Cache имеет лимит 10 ГБ и LRU-вытеснение.
  При превышении старые слои удаляются, и первый build после
  этого — медленный.
- Отладка усложняется: если build-push упал, надо смотреть
  конкретный matrix-инстанс, а не один общий job.

**Когда пересмотреть:**

- Если `pkg/**` меняется часто и пересборка всех сервисов
  съедает выгоду — рассмотреть отдельные триггеры по
  сервисам (какой сервис реально зависит от каких пакетов
  в `pkg/`).
- Если сервисов станет 8+ — возможно, стоит разделить
  workflow на несколько файлов (`ci.yml`, `cd-services.yml`).
- Если GitHub Actions Cache начнёт вытеснять важные слои —
  рассмотреть self-hosted registry (`type=registry`) вместо
  `type=gha`.

## Статус

**Реализовано** (2026-10-05).

Что сделано:

- **Docker layer caching** — `cache-from: type=gha` + `cache-to: type=gha,mode=max` во всех 4 build-push шагах. Обязательно с `docker/setup-buildx-action` — дефолтный драйвер `docker` не поддерживает cache export.
- **Matrix strategy** — `cd` job разбит на три: `changed-services` → `build-and-push` (matrix 4x) → `deploy`.
- **Deploy с условием** — `if: any_changed == 'true'` на шаге SSH-деплоя (защита от пустого pull).
- **`changed-files` расширен** — `.github/workflows/ci-cd.yml` тоже триггерит пересборку.
- **Интеграционные тесты в CI** — добавлен шаг `Run Integration Tests` с `go test -tags=integration -v -timeout=15m ./...` после smoke-build'ов. Закрывает ADR-007 CI-1.

Замеры после внедрения (при изменении 1 сервиса из 4):

| Фаза | Было | Стало |
|---|---|---|
| `cd`: 4 build-push | 6–16 мин | ~2 мин |
| Итого деплой | 10–18 мин | **~4 мин** |

Точные цифры зависят от прогрева кеша. Шаг `Run Integration Tests` добавляет к CI ещё ~3-5 минут (Testcontainers поднимает Postgres/Redis для каждой integration-группы).
