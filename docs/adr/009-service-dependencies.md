# ADR-009: Карта зависимостей сервисов

## Контекст

С ростом числа сервисов (Auth, Gateway, Profiles, Exercises, Habits, Workouts, Leaderboard) становится сложно удерживать в голове, кто кого зовёт. Без явной карты появляются:

- **Циклические зависимости.** Workouts → Profiles, Profiles → Workouts — оба падают, если один недоступен.
- **«Скрытые» зависимости.** Gateway знает про все, но никто не знает, что Gateway знает про все.
- **Размытая ответственность.** Логика «если A, то не пускай в B» оказывается не в том сервисе.
- **Рост Gateway в монолит наоборот.** Gateway начинает содержать бизнес-логику, потому что «ну он же всё равно видит все данные».

Нужны явные правила и карта. Обновлять карту при каждом новом сервисе — обязанность, не опция.

## Решение

### Карта зависимостей

**Поток клиента:**

```
Клиент → Gateway → {Auth, Profiles, Exercises, Habits, Workouts, Leaderboard}
```

Gateway — единая точка входа для клиента. Клиент **не ходит** к бизнес-сервисам напрямую.

**Внутренние вызовы (sync gRPC):**

```
Workouts → Profiles   (GetProfile — коэффициент при создании тренировки)
Workouts → Exercises  (GetExercise — name, description, type при работе с тренировкой)
```

**Планируется (уточнится отдельным ADR):**

```
Leaderboard → Workouts   (агрегация score — см. ADR-002 про /users/me)
Leaderboard → Profiles   (если нужны данные профиля в лидерборде)
```

### Правила

**1. Циклических зависимостей нет.**

Если A → B, то B **не должен** звать A. Иначе при недоступности одного падают оба, и нельзя задеплоить по отдельности.

Проверять при каждом новом вызове. Если очень нужен «обратный» вызов — это сигнал, что границы сервисов проведены неверно, либо нужна событийная шина (см. ADR-004).

**2. Gateway — только прокси + auth + агрегация.**

Gateway делает:
- Принимает HTTP от клиента.
- Валидирует JWT через Auth.
- Проксирует в нужный сервис по gRPC.
- Агрегирует несколько ответов в один (например, `GET /users/me` → Profiles + Workouts).

Gateway **не делает**:
- Бизнес-логику («если profile_completed=false, не пускай в Workouts» — это правило Workouts или Profiles, не Gateway).
- Хранение данных.
- Расчёты (score, коэффициенты, лидерборды).

Если ловишь себя на «в Gateway быстренько посчитаем» — стоп. Найди правильное место.

**3. Каждый сервис владеет своими данными.**

- Никто не читает таблицы чужого сервиса.
- Cross-service FK на уровне БД нет (см. ADR-004).
- Ссылки между сервисами — по ID без ограничений.
- Если сервису нужны данные соседа — только через его gRPC-контракт или копию (снапшот, см. ADR-001, ADR-008).

**4. Никаких «shared» таблиц.**

Если два сервиса хотят одну и ту же таблицу — это ошибка моделирования. Данные принадлежат одному сервису, остальные — читают через API.

**5. Один потребитель — не повод объединять сервисы.**

Если Workouts — единственный потребитель Exercises, это **не** значит, что их надо объединить. Exercises — самостоятельная сущность (справочник), у неё своя БД, свой lifecycle, свой админ-флоу. Завтра появится ещё потребитель (например, аналитика или мобильный офлайн-кэш).

**6. Events — только когда конкретно больно.**

См. ADR-004. Event-driven (Kafka/NATS) **не используется**. Если понадобится — отдельный ADR с обоснованием: какая боль, какая шина, какая схема событий, как обеспечивается идемпотентность.

### Целевое состояние

Статусы: ✅ — реализован, 🚧 — в работе, 📋 — в плане.

| Сервис | Статус | Зовёт | Его зовут |
|---|---|---|---|
| **Auth** | ✅ | — | Gateway |
| **Gateway** | ✅ | Auth, Profiles | клиенты |
| **Profiles** | ✅ | — | Gateway |
| **Exercises** | 🚧 | — | Gateway (план), Workouts (план) |
| **Habits** | 📋 | — | Gateway (план) |
| **Workouts** | 📋 | Profiles (план), Exercises (план) | Gateway (план), Leaderboard (план) |
| **Leaderboard** | 📋 | Workouts (план) | Gateway (план) |

Целевая карта зависимостей (после реализации всех сервисов):

```
Клиент → Gateway → {Auth, Profiles, Exercises, Habits, Workouts, Leaderboard}

Workouts → Profiles   (GetProfile)
Workouts → Exercises  (GetExercise)

Leaderboard → Workouts   (агрегация score)
```

Циклических зависимостей нет. Gateway — самый «связанный» узел, но это его роль.

## Последствия

**Плюсы:**

- Карта — единый источник истины про связи.
- Правила явные: не «как получится», а «вот так делаем».
- Легче дебажить: упал Workouts — знаешь, кто пострадал (Gateway, Leaderboard), кто нет (Auth, Profiles, Exercises).
- Легче деплоить: сервис без входящих зависимостей (Auth) деплоится независимо.

**Минусы:**

- Карта может устареть, если её не обновлять при каждом PR.
- Правила не автоматизированы — держатся на дисциплине.
- При росте числа сервисов карта станет сложнее, возможно, потребуется визуализация (mermaid-диаграмма).

**Когда пересмотреть:**

- Если появится циклическая зависимость — пересмотреть границы сервисов.
- Если Gateway начнёт содержать бизнес-логику — пересмотреть, где она должна жить.
- Если число сервисов превысит 10 — ввести автоматическую проверку через CI (например, анализ импортов).
- Перед каждым новым сервисом — обновить карту и правила, если меняются.
