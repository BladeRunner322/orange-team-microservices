# ADR-016: Сетевая безопасность периметра

## Контекст

При первой проверке периметра (nmap снаружи против `136.234.4.93`) выяснилось, что из интернета доступны все внутренние порты:

- `50051`, `50052`, `50053` — gRPC Auth/Profiles/Exercises
- `5432`, `5433`, `5434` — PostgreSQL
- `6379`, `6380` — Redis
- `8080`, `8082`, `8083` — HTTP health/metrics сервисов
- `8081` — Gateway

**Последствия:** любой из интернета мог подключиться к PostgreSQL, читать/писать Redis (refresh-токены, rate-limit-бакеты), дёргать gRPC-сервисы напрямую в обход Gateway и RBAC.

**Причина:** в `docker-compose.yml` каждый сервис имел `ports:` вида `${PORT}:${CONTAINER_PORT}`. Docker пробрасывает такие порты на `0.0.0.0` через собственные iptables-правила и **обходит ufw** — даже активный файрвол бы не помог.

Дополнительный фон: SSH на 22 порту — самый атакуемый порт в интернете. Без защиты в `/var/log/auth.log` накапливаются десятки-сотни неудачных попыток в сутки от ботов.

## Решение

Четыре независимых слоя защиты.

### 1. Bind внутренних портов к `127.0.0.1`

В `docker-compose.yml` все `ports:` (кроме Caddy) изменены с:

```yaml
- "${PORT}:${CONTAINER_PORT}"
```

на:

```yaml
- "127.0.0.1:${PORT}:${CONTAINER_PORT}"
```

**Что это даёт:**
- Порт доступен **только с самого сервера** (`localhost:5432` работает).
- Снаружи (`136.234.4.93:5432`) — недоступен.
- Внутри docker-сети всё работает по именам `auth-service:50051`, `postgres-auth:5432` — bind на `127.0.0.1` тут ни при чём, сервисы общаются через docker DNS.

**Исключение — Caddy.** У него `0.0.0.0:80` и `0.0.0.0:443`, потому что он единственный сервис, который должен быть доступен из интернета. Caddy проксирует в `gateway:8081` по docker DNS, а не через хост.

### 2. ufw — только 22, 80, 443

```
ufw default deny incoming
ufw default allow outgoing
ufw allow 22/tcp    # SSH
ufw allow 80/tcp    # HTTP (Caddy, редирект)
ufw allow 443/tcp   # HTTPS (Caddy)
ufw enable
```

**Что это даёт:**
- Default deny — любой новый сервис, случайно поднятый на `0.0.0.0`, автоматически закрыт, пока не разрешён явно.
- Защита для процессов вне Docker (`go run`, `python -m http.server`, что угодно) — Docker iptables не участвует, ufw закрывает.
- Двойная защита: если Docker iptables-правило сломается (обновление, баг) — ufw всё равно закроет.
- Декларация периметра: `ufw status` показывает актуальную картину.

**Почему не закрываем 22:**
SSH нужен для ручного доступа к серверу (сам админ) и для CD (`appleboy/ssh-action`). Закрытие 22 = потеря доступа и потеря возможности деплоить.

### 3. fail2ban на SSH

Установлен `fail2ban` с дефолтным SSH-jail и кастомным `/etc/fail2ban/jail.local`:

```
[DEFAULT]
bantime = 1h
findtime = 10m
maxretry = 5

[sshd]
enabled = true
```

**Как работает:** после 5 неудачных попыток SSH с одного IP — бан на час через ufw. Все новые попытки с этого IP дропаются до истечения бана.

**Что это даёт:**
- Боты, перебирающие пароли `root/admin/123456`, отсекаются после 5 попыток. До SSH их пакеты больше не доходят.
- Логи `/var/log/auth.log` перестают расти от фонового шума.
- Меньше нагрузки на CPU.

**Что это НЕ даёт:**
- Не защищает от брутфорса пароля (пароль отключён, только ключи).
- Не защищает от атак через 80/443.
- Не заменяет правильную настройку SSH (`PasswordAuthentication no`, `PermitRootLogin prohibit-password`).

### 4. gRPC `insecure` между сервисами — осознанный выбор

Gateway ходит к Auth/Profiles/Exercises с `GRPC_CLIENT_TLS_MODE=insecure` (TLS есть, но сертификат не проверяется).

**Почему это ок сейчас:**
- Все 4 сервиса живут в **одной docker-сети**. Наружу их gRPC-порты не проброшены (см. пункт 1).
- MITM в docker-сети может устроить только тот, кто уже внутри — то есть уже скомпрометировал контейнер или сервер.
- gRPC-сертификаты self-signed с `CN=localhost`, а клиенты подключаются к `auth-service:50051`. Для `verify` нужны нормальные сертификаты с правильными SAN — это отдельная работа на 2-3 часа.

**Почему не `verify`:**
- Сейчас нет реального вектора атаки, который бы `verify` закрывал.
- `mTLS` в ADR-004 уже помечен как Level C — «только при выходе из одной docker-сети».
- Преждевременная оптимизация безопасности — как и любая преждевременная оптимизация — тратит время без выгоды.

**Триггеры для перехода на `verify` + mTLS:**
- Сервисы выйдут из одной docker-сети (несколько хостов, разные окружения).
- Появится внешний потребитель gRPC (не через Gateway).
- Аудит или compliance-требования.

**Статус:** C-3 в ADR-007 закрывается как «осознанное решение», а не как «недоделка».

## Последствия

**Плюсы:**

- Снаружи доступны только 22, 80, 443. Проверено nmap'ом: все внутренние порты — `filtered` (пакеты дропаются), не `open`.
- Двойной слой: bind на `127.0.0.1` + ufw. Падение одного слоя не открывает периметр.
- Боты на SSH отсекаются после 5 попыток, логи чистые.
- Периметр декларативен: `ufw status` + `docker-compose.yml` — единый источник истины.
- Защита для процессов вне Docker (если однажды поднимешь что-то руками).
- Никаких преждевременных сложностей: `insecure` gRPC — обоснованное решение, а не недоделка.

**Минусы:**

- Ручной шаг при добавлении нового сервиса: если у него есть публичный порт (как у Caddy), нужно явно разрешить в ufw. Если внутренний — просто bind на `127.0.0.1`.
- fail2ban иногда банит соседние IP из Selectel (в логах видно `136.234.4.130` — соседний VDS, сканирующий подсеть). Это не баг, но при отладке из соседнего контейнера может ввести в заблуждение.
- `insecure` gRPC остаётся техническим долгом — но осознанно, с триггерами и без иллюзий.

**Когда пересмотреть:**

- При выходе из одной docker-сети → mTLS, `verify`, отдельный CA.
- При появлении внешних gRPC-потребителей → `verify` + валидные сертификаты.
- При появлении второго сервера / второго окружения → SSH только через bastion или VPN.
- При росте количества сканирований SSH → ужесточить fail2ban (`bantime=24h`, `maxretry=3`) или сменить порт SSH на нестандартный.
- Если появится SIEM/аудит → централизованный сбор логов ufw и fail2ban.
