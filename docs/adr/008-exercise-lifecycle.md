# ADR-008: Жизненный цикл упражнения

## Контекст

В монолите упражнения были справочником без UPDATE и DELETE:
- `CreateExercise` — создание
- `GetExercise(id)` — чтение одного
- `GetExercises()` — чтение списка

Админ мог только создавать. Исправить опечатку в названии или удалить устаревшее упражнение — нельзя, только через прямой SQL в БД.

При переносе в микросервис появляются новые вопросы:

- **Что делать с `type`?** В `workout_exercises` для weight-типа хранятся `weight/sets/reps`, для duration — `duration`. Если поменять тип, старые записи станут невалидными.
- **Что делать с `difficulty`?** Оно участвует в расчёте `workout_score`. Если менять, пересчитывать старые тренировки — несправедливо (пользователь уже получил очки, они в лидерборде).
- **Что делать с `name`/`description`?** Это отображаемые данные. Опечатки в них — нужно исправлять.
- **Что делать с DELETE?** На упражнения ссылаются `workout_exercises`. Hard delete сломает исторические тренировки.

Нужны явные правила, иначе через месяц непонятно, что было решением, а что — упущением.

## Решение

Четыре правила для жизненного цикла упражнения.

### 1. `type` — immutable

После создания `type` менять нельзя. В proto `PatchExercise` не принимает это поле.

**Причина:** смена `weight` → `duration` (или наоборот) ломает существующие `workout_exercises`. У weight-типа есть `weight/sets/reps`, у duration — `duration`. Валидация `ValidateForWorkoutExerciseType` перестанет проходить.

Если нужно «поменять тип» — удалить упражнение и создать новое.

**В `workout_exercises` `type` не снапшотится.** Workouts берёт его live через `Exercises.GetExercise(id)` при создании и патче `workout_exercise`. Это безопасно, потому что `type` immutable — его значение всегда совпадает с моментом создания.

Следствие: Workouts → Exercises вызывается не только при чтении (для `name`/`description`), но и при записи (для `type`).

### 2. `difficulty` — снапшот

При создании `workout_exercise` Workouts копирует `difficulty` упражнения в свою запись. При пересчёте `workout_score` использует **свою копию**, не зовёт Exercises.

Следствие: админ может менять `difficulty` свободно. Старые тренировки не пересчитываются — их `workout_score` фиксирован. Новые создаются с новым значением.

Это тот же принцип, что в ADR-001 для `personal_score_coefficient` — снапшот на момент создания.

### 3. `name`, `description` — live

При чтении тренировки (`GET /workouts/{id}` и `/workouts/{id}/exercises`) Workouts зовёт `Exercises.GetExercise(id)` для получения актуального названия и описания.

Следствие: если админ исправит опечатку — она исправится **везде**, включая старые тренировки.

Осознанный компромисс: имя упражнения — часть истории, но не «застывшая». Пользователь, открывающий тренировку через год, увидит актуальное название, а не исторически ошибочное.

### 4. DELETE — soft

Удаление упражнения ставит флаг `deleted_at`, физически запись не удаляется.

- `GetExercises()` (список для клиента) — **только активные** (`deleted_at IS NULL`).
- `GetExercise(id)` — **возвращает и удалённые**, с флагом `is_deleted`. Это нужно Workouts, чтобы показать исторические тренировки.

Gateway сам решает, что делать с флагом:
- `GET /exercises/{id}` от клиента — можно вернуть 404, если удалено.
- Внутренний вызов из Workouts — использовать как есть.

### 5. `PatchExercise` доступен только admin

Поля, доступные в PATCH: `name`, `description`, `difficulty`. Все — опциональные через nullable.

`type` — не входит.

## Последствия

**Плюсы:**

- Старые тренировки не ломаются при правке справочника.
- `workout_score` фиксирован — лидерборд справедлив.
- Опечатки в названиях исправляются везде.
- История тренировок сохраняется даже после «удаления» упражнения.
- Нет каскадных пересчётов при изменении справочника.

**Минусы:**

- Workouts вынужден звать Exercises при чтении тренировки. Это sync-зависимость в runtime (см. ADR-004 — это осознанный выбор).
- **N+1 при чтении списка.** `GET /workouts` (20 тренировок × 10 упражнений) даст 200 вызовов `GetExercise(id)` или 20 батчей. **Осознанно принимаем для MVP** — объём мал, latency приемлема. Batch `GetExercisesByIds` — когда станет горячо (см. «Когда пересмотреть»).
- Копия `difficulty` в `workout_exercises` дублирует данные. Технический долг: если решим менять `difficulty` ретроактивно — придётся делать миграцию.
- Soft delete требует фильтра `deleted_at IS NULL` в каждом запросе списка.

**Когда пересмотреть:**

- Если Sync-вызов Workouts → Exercises станет горячим — кэш в Workouts или batch-метод `GetExercisesByIds`.
- Если потребуется **ретроактивный пересчёт** очков (например, при обнаружении бага в difficulty) — отдельный ADR и миграция.
- Если появятся «версии» упражнения (например, изменения методики) — отдельная сущность, не текущее поле.
