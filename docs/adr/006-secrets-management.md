# ADR-006: Управление секретами

## Контекст

В проекте **5 файлов `.env`**:

- Корневой `.env` — для `infra/docker-compose.yml` (хост-порты, Grafana password).
- `services/auth/.env` — Auth Service.
- `services/gateway/.env` — Gateway Service.
- `services/profiles/.env` — Profiles Service.
- `services/exercises/.env` — Exercises Service.

Все они в `.gitignore` и **не попадают в git**. В репозитории — только `.env.example` (шаблоны).

**Проблема при деплое:** CD workflow делает `git pull origin main` на сервере, но `.env` файлы **не подтягиваются** — они не в git. Если в новой версии появилась новая переменная (например, `PROFILES_GRPC_ADDR`), сервис на сервере **упадёт при старте**, потому что в старых `.env` её нет.

**Текущий процесс обновления секретов:**
1. Изменить `.env.example` локально и закоммитить.
2. Подключиться к серверу по SSH.
3. Открыть `.env` через `nano`.
4. Добавить новую переменную.
5. Сохранить.
6. Только после этого — деплой.

Это **ручная работа**, которая накапливается с каждым изменением. Плохо для масштабирования.

**Что нужно:** автоматизировать обновление `.env` файлов на сервере. Изменения должны происходить **через git**, а CD — сам раскладывать актуальные `.env`.

## Рассмотренные варианты

**A) Коммитить `.env` в git.**
- Плюсы: 10 минут настройки, полная автоматизация.
- Минусы: секреты в открытом виде. Даже в приватном репо — риск утечки. Не прод-подход.

**B) SOPS + age.**
- Плюсы: шифрование в git, автоматизация, промышленный стандарт, без SaaS.
- Минусы: настройка ~2 часа.
- **Выбран.**

**C) Валидация `.env` в CD.**
- Плюсы: ловит ошибки раньше.
- Минусы: **не решает** проблему — всё равно ручная правка на сервере.
- Оставить как **дополнение** в будущем.

**D) GitHub Secrets + base64 + scp.**
- Плюсы: секреты в GitHub Secrets, автоматизация.
- Минусы: при **каждом** изменении `.env` нужно обновлять GitHub Secret вручную. Ручной работы не меньше, только в другом месте.

**E) HashiCorp Vault.**
- Плюсы: максимальная безопасность, централизованность.
- Минусы: оверкилл для проекта. Нужно поднимать и администрировать Vault, менять код приложения.

**F) Doppler / Infisical (SaaS).**
- Плюсы: простой UI, быстрая настройка.
- Минусы: зависимость от третьей стороны, секреты у вендора.

## Решение

**SOPS + age.**

### Что это

**age** — асимметричное шифрование:
- **Публичный ключ** — только шифрует. Хранится в `.sops.yaml` в git.
- **Приватный ключ** — только расшифровывает. Хранится в GitHub Secret и локально.

**SOPS** — инструмент, который использует age для шифрования значений в файлах (`.env`, YAML, JSON). Ключи остаются видимыми, значения — шифруются.

### Как работает

**Шифрование (локально):**
1. Меняешь `.env`.
2. `sops --encrypt services/auth/.env > services/auth/.env.enc`.
3. Коммитишь `.env.enc` в git.

**Расшифровка (в CD):**
1. CD берёт приватный age-ключ из GitHub Secret.
2. `sops --decrypt services/auth/.env.enc > services/auth/.env`.
3. Копирует `.env` на сервер через `scp-action`.
4. `docker compose up` — работает с расшифрованными `.env`.

### Формат зашифрованного файла

```
GRPC_PORT=:50051
JWT_SECRET=ENC[AES256_GCM,data:8f3k...,iv:...,tag:...,type:str]
POSTGRES_PASSWORD=ENC[AES256_GCM,data:7x2p...,iv:...,tag:...,type:str]
sops_lastmodified: 2026-09-30T...
sops_mac: ENC[AES256_GCM,data:...,type:str]
```

Ключи открыты — для читаемости git diff. Значения зашифрованы — восстановить без приватного ключа невозможно.

### Что в git, что вне

**В git:**
- `.sops.yaml` — конфиг (публичный age-ключ).
- `services/*/.env.enc` — зашифрованные `.env`.
- `.env.example` — шаблоны (для документации).

**Вне git:**
- `services/*/.env` — реальные, расшифрованные (в `.gitignore`).
- Приватный age-ключ (`key.txt`) — только локально + GitHub Secret.

## Последствия

**Плюсы:**

- **Полная автоматизация.** Меняешь `.env` локально → encrypt → commit → push → CD сам расшифровывает и раскладывает.
- **Никаких `nano` на сервере.** И никаких GitHub Secrets для каждой переменной.
- **Секреты в git — но зашифрованы.** Даже если репо утечёт — без приватного age-ключа `.env.enc` бесполезен.
- **История изменений.** `git log` по `.env.enc` покажет, когда менялся `JWT_SECRET` (ключи видны, значения — нет).
- **Промышленный стандарт.** Используется в Mozilla, Grafana Labs, многих GitOps-проектах.
- **Без SaaS.** Всё у тебя: age-ключи, SOPS, git.

**Минусы:**

- **Настройка ~1.5–2 часа.** Нужно установить age и sops, сгенерировать ключи, настроить `.sops.yaml`, обновить CD.
- **Приватный age-ключ = единственная ценность.** Если он утечёт — все `.env.enc` скомпрометированы. Хранить только локально + GitHub Secret.
- **SOPS добавляет метаданные.** Каждый зашифрованный файл имеет `sops_lastmodified`, `sops_mac`. Diff чуть шумнее.
- **Нужен age-ключ на каждой машине разработчика.** Если работаешь с нескольких устройств — придётся копировать приватный ключ.

**Когда пересмотреть:**

- Если появится **команда** и станет критично — перейти на **HashiCorp Vault** или **k8s External Secrets Operator**.
- Если проект **перейдёт в k8s** — вместо SOPS использовать **Sealed Secrets** (то же шифрование, но нативно для k8s).
- Если **появятся аудиторские требования** — перейти на managed secret manager (AWS Secrets Manager, GCP Secret Manager).

## Rotation age-ключа

Если приватный age-ключ скомпрометирован (утечка ноутбука, случайный коммит, публикация в чате), процедура:

1. Сгенерировать новую пару: `age-keygen -o key.txt`.
2. Обновить `.sops.yaml` — заменить `age:` в каждой creation_rule на новый публичный ключ.
3. Перешифровать все `.env.enc`:
   ```bash
   task sops:decrypt   # старым ключом
   task sops:encrypt   # новым ключом
   ```
4. Обновить `SOPS_AGE_KEY` в GitHub Secrets.
5. Удалить старый приватный ключ локально.
6. Закоммитить обновлённые `.env.enc` и `.sops.yaml`.

**Ротация ключа не спасает, если старый приватный ключ уже утёк** — прошлые версии `.env.enc` в git-истории остаются читаемыми старым ключом. В этом случае:
- Ротировать также сами секреты, которые были в `.env` (JWT_SECRET, пароли PostgreSQL, Redis).
- Опционально — переписать git-историю (`git filter-repo`), но это ломающее изменение для всех клонов.

**Профилактика:** приватный age-ключ не коммитится (в `.gitignore`), не светится в логах CI (`set -x`), хранится в 1Password / KeePass + GitHub Secret.

## Дополнительно

**Валидация `.env` в CD — ✅ реализовано** (2026-10-06):

В `.github/workflows/ci-cd.yml` перед `docker compose up`:
- Сравниваются переменные из `.env.example` с расшифрованным `.env`.
- Если чего-то не хватает — workflow падает с понятной ошибкой **до** старта сервисов.

Это не замена SOPS, а **страховка** от рассинхрона между `.env.example` и `.env.enc`.

## Эксплуатационные заметки

**SSH-ключ для CD — только RSA, не Ed25519.**

CD-деплой использует `appleboy/ssh-action@v1.0.3` (актуально на октябрь 2026). Эта версия **не умеет парсить Ed25519** из env-секрета `SERVER_SSH_KEY` — падает с ошибкой:

```
ssh: handshake failed: ssh: unable to authenticate,
attempted methods [none], no supported methods remain
```

Соединение с сервером устанавливается, но клиент не предлагает ни одного метода аутентификации, потому что не смог собрать `ssh.Signer` из строки ключа.

Для `SERVER_SSH_KEY` создан **отдельный RSA-ключ** `~/.ssh/orange_deploy_rsa` (не личный `id_ed25519`), публичная часть которого добавлена в `/root/.ssh/authorized_keys` на продакшн-сервере. Такой подход также безопаснее: компрометация ключа для CD не затрагивает личный SSH-доступ.

**При ротации ключа:** либо создать новый RSA (тот же алгоритм), либо обновить `appleboy/ssh-action` до v1.2+ — там баг с Ed25519 исправлен.
