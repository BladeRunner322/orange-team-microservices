# ADR-023: Сервис привычек (Habits)

## Контекст

Проект развивается от монолита к набору микросервисов. Уже реализованы Auth, Gateway, Profiles, Exercises. Следующий по плану — Habits.

Задача Habits — трекер привычек. Пользователь заводит привычку («Пить воду», «Читать 20 минут»), ежедневно отмечает выполнение, видит свой стрик — сколько дней подряд он держится.

**Чем Habits отличается от Exercises.** На первый взгляд похоже — CRUD над сущностью. Но есть принципиальная разница:

| | Exercises | Habits |
|---|---|---|
| Кто создаёт | Admin | Сам пользователь |
| Для кого | Общий справочник для всех | Индивидуально у каждого |
| Пример | «Жим лёжа» | «Пить воду» |
| Аналог в жизни | Каталог товаров | Личный список дел |
| Роль | Справочник | Личный трекер |

Habits — **не каталог**. Это личные привычки пользователя. Никаких админов, никакого общего списка.

## Решение

### 1. Модель данных

Две таблицы: **habits** (сами привычки) и **habit_completions** (отметки о выполнении).

**`habits`:**

| Поле | Тип | Комментарий |
|---|---|---|
| `id` | UUID PK | |
| `user_id` | UUID | Владелец. Приходит из metadata |
| `name` | VARCHAR(100) | 1–100 символов, trim |
| `description` | VARCHAR(500) | 0–500 символов, может быть NULL/пусто |
| `created_at` | TIMESTAMPTZ NOT NULL DEFAULT NOW() | |
| `updated_at` | TIMESTAMPTZ | NULL пока не менялось |
| `deleted_at` | TIMESTAMPTZ | NULL пока не удалено (soft delete) |

**`habit_completions`:**

| Поле | Тип | Комментарий |
|---|---|---|
| `habit_id` | UUID FK | Ссылка на `habits.id` (без cross-service FK) |
| `date` | DATE | За какой день засчитано |
| `created_at` | TIMESTAMPTZ NOT NULL DEFAULT NOW() | Когда реально нажали кнопку |

**Уникальный индекс** `(habit_id, date)` — нельзя отметить один день дважды. Concurrent-отметки обрабатываются атомарно через `ON CONFLICT DO NOTHING`.

**Почему две таблицы.** Одна привычка — много отметок. Если хранить даты в одном поле (массив, JSON), то:
- «Отметь сегодня» → read-modify-write с гонкой.
- «Все выполнения за октябрь» → надо вытащить весь массив и фильтровать в коде.
- Нет индекса по дате → тяжёлые запросы.
- Нельзя связать с чем-то ещё (заметка к выполнению, аудит).

Одна строка — одна отметка. Так устроены все трекеры.

### 2. Частота привычек

**Только ежедневные.** Каждый день — либо выполнено, либо нет.

Сложные расписания («3 раза в неделю», «по будням») — не в MVP. Если понадобится, отдельный ADR с расширением схемы (`frequency` + `schedule` в `habits`) и пересчётом стриков.

### 3. Стрик

**Не хранится.** Вычисляется на лету из `habit_completions`.

**Алгоритм:** идём от сегодняшнего дня назад, считаем подряд идущие даты с отметками. Останавливаемся на первом пропуске.

**Стрик держится до конца дня.** Если сегодня ещё не отмечено, но вчера было — стрик пока не сломан. Сломается только когда сегодняшний день закончится без отметки. Это стандартное поведение трекеров — пользователь должен успеть до конца дня.

**Timezone — UTC.** Храним даты без времени. Все пользователи в UTC. Timezone в профиль добавим позже, если понадобится.

### 4. Отметка задним числом

**До 7 дней назад.** Пользователь забыл отметить вчера — может отметить сегодня. Помечает, что за прошлую дату. Стрик пересчитывается.

**Снятие отметки — тоже 7 дней.** Симметрично. Случайно нажал «выполнено» — можно отменить в течение недели. Дальше нельзя (поздно, старый стрик трогать нельзя).

**Будущее — нельзя.** Отметить заранее нельзя. Только сегодня и назад.

### 5. Патч привычки

**Что можно менять:** `name`, `description`.
**Что нельзя:** `user_id`, `id`, `created_at`.

Патч привычки — это изменение **самой привычки**. Отметки выполнения — **отдельная операция**, не патч. Они меняют разные таблицы и вызываются разными endpoint'ами.

### 6. Soft delete

DELETE помечает `deleted_at`. Физически не удаляется.

**Completions остаются.** Если привычка восстанавливается — история на месте. В API список активных (`deleted_at IS NULL`), но `GetHabit(id)` возвращает и удалённые (с флагом).

### 7. Лимит количества привычек

**Не ограничиваем.** Пользователь может создать сколько угодно. Если станет проблемой — добавим лимит позже.

### 8. gRPC-методы

```
HabitsService:
  CreateHabit(CreateHabitRequest) returns (Habit)
  GetHabit(GetHabitRequest) returns (Habit)
  GetHabits(GetHabitsRequest) returns (GetHabitsResponse)   # со стриками
  PatchHabit(PatchHabitRequest) returns (Habit)
  DeleteHabit(DeleteHabitRequest) returns (DeleteHabitResponse)
  CompleteHabit(CompleteHabitRequest) returns (CompleteHabitResponse)
  UncompleteHabit(UncompleteHabitRequest) returns (UncompleteHabitResponse)
  GetCompletions(GetCompletionsRequest) returns (GetCompletionsResponse)
```

**`GetHabits` возвращает стрики.** Один вызов — список привычек с текущим стриком и флагом «выполнено сегодня». Не отдельный вызов на каждую привычку.

### 9. HTTP-маршруты через Gateway

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/habits` | Список привычек со стриками |
| POST | `/habits` | Создать |
| GET | `/habits/{habitId}` | Одна привычка |
| PATCH | `/habits/{habitId}` | Патч (name, description) |
| DELETE | `/habits/{habitId}` | Soft delete |
| POST | `/habits/{habitId}/complete` | Отметить (сегодня или с `date` в теле) |
| DELETE | `/habits/{habitId}/complete` | Снять отметку |
| GET | `/habits/{habitId}/completions` | История за период |

**`user_id` приходит из JWT.** Gateway пробрасывает через gRPC metadata (`x-user-id`), Habits читает из context.

### 10. Валидация

- `name` — 1–100 символов после trim.
- `description` — 0–500 символов после trim, может быть пустым.
- `date` при отметке — не позже сегодня, не раньше 7 дней назад.
- `date` при снятии — те же границы.

Специальные символы не запрещаем (кроме trim). Emoji, кавычки, тире — всё допустимо.

### 11. Идентификаторы и порты

По ADR-005:
- gRPC — следующий свободный: **50054** (Docker) / **50064** (локально).
- HTTP (health/ready/metrics) — **8084** (Docker) / **8094** (локально).
- PostgreSQL — **5435** на хосте.

### 12. Связи с другими сервисами

**Нет.** Habits не зовёт Profiles, Exercises, Workouts. Только свои таблицы. `user_id` приходит как данные из metadata.

Если понадобится показывать имя пользователя рядом с привычкой (для шаринга стриков?) — тогда Habits → Profiles. Пока такого требования нет.

## Последствия

**Плюсы:**

- Простой сервис без cross-service вызовов. Похож на Exercises, но с историей выполнений.
- Стрик не хранится → нет дрейфа, всегда актуален.
- Одна отметка = одна строка. Быстрые запросы, атомарные отметки, легко расширять.
- Soft delete сохраняет историю.
- 7-дневное окно для отметок и снятий — компромисс между «удобно исправить ошибку» и «нельзя переписать далёкое прошлое».

**Минусы:**

- Стрик считается на лету → `GetHabits` может тормозить на больших историях. Для MVP ок, при росте — кэш в Redis на 1 день.
- Timezone UTC — не учитывает пользователей из разных зон. Пока пользователей мало, ок. При росте — добавляем `timezone` в Profiles и используем в Habits.
- Только ежедневные привычки. Для «3 раза в неделю» нужен отдельный ADR.

**Когда пересмотреть:**

- Если `GetHabits` начнёт тормозить → кэш стриков в Redis или материализованное представление.
- Если понадобятся привычки с расписанием (не ежедневные) → отдельный ADR.
- Если появится шаринг стриков между пользователями → Habits → Profiles.
- Если появится timezone у пользователя → использовать при вычислении «сегодня».
- Если понадобятся «напоминания» → push-уведомления, отдельная тема.
