# ADR-013: Требования к инфраструктуре

## Контекст

Проект развивается от монолита к 7 микросервисам. На каждом этапе требования к серверу растут — добавляются новые PostgreSQL, Go-сервисы, растёт нагрузка на мониторинг.

Без зафиксированных цифр:

- Непонятно, когда текущий сервер перестанет справляться.
- Каждый раз при добавлении сервиса — гадание «а хватит ли».
- Нет ориентира для бюджета и выбора провайдера.
- Нет ответа на вопрос «когда переезжать на managed-сервисы или k8s».

Первая версия проекта уже прошла через **450 МБ RAM / 1 vCPU с swap** — на этом стек работал, но с трудом:

- Postgres + Docker daemon + OS съедали всю RAM.
- OOM killer убивал контейнеры при пиках.
- Сборки и деплой шли через swap (10-100x медленнее).
- Мониторинг (Prometheus, Loki, Grafana) пришлось отключать.

Сейчас проект на **8 ГБ RAM / 4 vCPU / 80 ГБ NVMe** — этого хватает на 4 сервиса (Auth, Gateway, Profiles, Exercises).

## Решение

Зафиксировать требования к серверу на **каждом этапе** жизненного цикла проекта.

### Текущее состояние (4 сервиса)

Контейнеры: 4 сервиса + 3 PostgreSQL + 2 Redis + Prometheus + Grafana + Loki + Promtail + Docker daemon + OS ≈ **15 контейнеров**.

| Параметр | Минимум | Комфортно |
|---|---|---|
| **RAM** | 4 ГБ | 8 ГБ |
| **CPU** | 2 vCPU | 4 vCPU |
| **Диск** | 60 ГБ SSD | 80+ ГБ NVMe |

**Проверено на:** Selectel VDS (8 ГБ / 4 vCPU / 80 ГБ NVMe).

### Полная архитектура (7 сервисов)

Контейнеры: 7 сервисов + 7 PostgreSQL + 2 Redis + Prometheus + Grafana + Loki + Promtail + Docker daemon + OS ≈ **25 контейнеров**.

| Параметр | Минимум | Комфортно | С запасом на прод |
|---|---|---|---|
| **RAM** | 8 ГБ | 16 ГБ | 32 ГБ |
| **CPU** | 4 vCPU | 4-6 vCPU | 8 vCPU |
| **Диск** | 100 ГБ SSD | 200 ГБ NVMe | 500 ГБ NVMe |

**Что потребляет больше всего:**

1. **7 PostgreSQL** — самый крупный пожиратель. Каждый инстанс держит `shared_buffers` (по умолчанию 128 МБ) + WAL + connection pool + служебные процессы. Суммарно 1-1.7 ГБ RAM.
2. **Prometheus + Loki** — 500 МБ – 1 ГБ RAM и 20-50 ГБ диска на хранение метрик и логов за 15-30 дней.
3. **7 Go-сервисов** — под нагрузкой 700 МБ – 1 ГБ RAM, idle — ~350 МБ.

## Последствия

**Плюсы:**

- Понятно, когда апгрейдить сервер (4 → 8 ГБ на этапе 4-5 сервисов, 8 → 16 ГБ на этапе 6-7 сервисов).
- Легче планировать бюджет.
- Зафиксированы триггеры для перехода на managed-сервисы или k8s.

**Минусы:**

- Цифры приблизительные — реальное потребление зависит от нагрузки.
- При росте пользователей (не только сервисов) потребуется пересчёт.
- Требования будут меняться с каждым новым ADR и оптимизацией.

**Когда пересмотреть:**

- **RAM > 8 ГБ, один сервер не тянет** → разнести по 2-3 VPS или перейти на k8s.
- **Postgres тормозит на I/O** → managed PostgreSQL (Selectel Managed DB, AWS RDS).
- **Мониторинг мешает бизнес-сервисам** → вынести Prometheus + Loki на отдельный VPS.
- **Нужен zero-downtime деплой** → k8s (rolling updates из коробки).
- **Сервисов > 8** → k8s + Service Mesh (Istio, Linkerd).
- **Команда > 3-4 разработчиков** → разделять окружения (staging, prod).

## Практические замечания

### Почему не один Postgres на всё

Database per Service (ADR-004) требует отдельный Postgres для каждого сервиса. Это **правильно** с точки зрения изоляции, но **дорого** по RAM. Компромисс — 7 баз в одном физическом Postgres с отдельными схемами и пользователями. Нарушает ADR-004, но экономит ~1 ГБ RAM. Отдельный ADR, если понадобится.

### Мониторинг можно отключать

Если бюджет ограничен, `task monitoring-down` + `task logging-down` освобождают **300-500 МБ RAM**. Для staging это часто оправдано. Для прода — нет (без метрик и логов не отладишь инциденты).

### Версии monitoring-образов не закреплены

В `docker-compose.yml` четыре сервиса мониторинга используют тег `:latest`:

```yaml
prometheus:
  image: prom/prometheus:latest
grafana:
  image: grafana/grafana:latest
loki:
  image: grafana/loki:latest
promtail:
  image: grafana/promtail:latest
```

Остальные образы закреплены (`postgres:18.6-bookworm`, `redis:7-alpine`, `caddy:2-alpine`, `migrate/migrate:v4.19.1`).

**Чем это плохо:** `docker compose pull` может притянуть мажорное обновление (например, Loki 3.x с ломающейся конфигурацией `pipeline_stages`), сервис не стартует, а CD уже прошёл. Отладка неочевидна — код не менялся, а сервис упал.

**Что делать:** закрепить мажорную версию (`prom/prometheus:v3`, `grafana/grafana:11`, `grafana/loki:3`, `grafana/promtail:3`). Минорные и патч-обновления внутри мажорной ветки остаются — `pull` их подтянет.

**Приоритет:** низкий. Триггер — первый инцидент из-за несовместимого обновления monitoring-образа.

### Мини-ПК как альтернатива VPS

Собственный мини-ПК (16 ГБ RAM) за ~15 000 ₽ окупается за 8-12 месяцев при цене VPS 1500-2000 ₽/мес. Плюсы — свои ресурсы без оверселла. Минусы — нет статического IP, зависимость от домашнего электричества/интернета, безопасность на тебе. Для MVP и обучения — интересный вариант. Для прода — не подходит без дополнительных мер (Cloudflare Tunnel, отдельный VPS как резервный канал).

### Managed-сервисы vs. self-hosted

Когда проект дорастёт до 7 сервисов, станет выгоднее держать **Postgres в managed** (Selectel Managed DB, AWS RDS). Плюсы:

- Бэкапы из коробки.
- Автоматический failover.
- Мониторинг БД из коробки.
- Не занимает RAM на основном сервере.

Минусы:

- Дороже (managed Postgres ~500-1000 ₽/мес за инстанс).
- Нельзя зайти в файловую систему.
- Зависимость от провайдера.

Переход на managed — отдельный ADR, когда придёт время.

### Бэкапы БД

**Реализовано** (2026-10-06). Скрипт `scripts/backup-db.sh` дампит три базы
(`auth_db`, `profiles_db`, `exercises_db`), сжимает и ротирует по 7 дней.
Запускается через cron на сервере.

**Off-site — ADR-014.** ✅ Реализовано (2026-10-07). Бэкапы выгружаются в Selectel Object Storage (`s3://orange-team-backups/`) через rclone. Ротация в S3 — 30 дней, локально — 7 дней. RPO = 24 ч, RTO = 2 ч.

Redis не бэкапится — там только refresh-токены и rate-limit-вёдра с TTL,
потеря некритична.
