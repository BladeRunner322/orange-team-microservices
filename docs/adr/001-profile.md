# ADR-001: Профиль пользователя

## Контекст

В монолите данные пользователя жили в одной таблице `app.users`:

- credentials (email, password_hash) — кто ты
- профиль (sex, weight_grams, birth_date, height_cm) — данные о тебе
- role — что тебе можно
- user_workout_score — накопленный счёт

При распиле на микросервисы:

- **Auth** владеет credentials и role
- **Profiles** владеет профилем
- Встал вопрос: **когда** создаётся запись в Profiles и что делать с пустым профилем

В монолите профиль был необязательным — можно было зарегистрироваться и никогда не заполнить вес/рост. `personal_score_coefficient` в `CreateWorkout` возвращал `1`, если `weight_grams` или `height_cm` NULL:

```go
if user.WeightGrams == nil || user.HeightCM == nil {
    return 1
}
```

То есть пустой профиль не блокировал создание тренировок.

## Решение

- **Владелец профиля:** Profiles-сервис.
- **Когда создаётся:** лениво, при первом чтении профиля из Profiles-сервиса. Не важно, кто читает — сам пользователь (`GetMyProfile`, `user_id` из metadata) или другой сервис (`GetProfile(user_id)`, `user_id` в теле запроса). Auth не уведомляет Profiles при регистрации.
- **Обязательные поля в БД:** нет. `sex`, `weight_grams`, `birth_date`, `height_cm` — все nullable (запись создаётся лениво, до заполнения профиля). Но для **создания тренировки** все 4 поля должны быть заполнены — см. следующий пункт.
- **Пустой профиль:** допустим **для хранения**, но **не для создания тренировки**.
  - Profiles создаёт пустую запись при первом чтении профиля (lazy-create) — через `GetMyProfile` или `GetProfile`.
  - Profiles возвращает профиль с флагом `profile_completed` (все 4 поля заполнены).
  - Workouts при `CreateWorkout` требует `profile_completed = true`. Иначе возвращает `FailedPrecondition`.
- **Профиль считается заполненным**, если заданы все четыре поля: `sex`, `weight_grams`, `birth_date`, `height_cm`.
- **Принцип снапшота:** `personal_score_coefficient` тренировки фиксируется в момент её создания. При изменении профиля старые тренировки **не пересчитываются**.
- **Никаких событий и sync-вызовов Auth → Profiles** при регистрации.

## Последствия

**Плюсы:**

- Нет инфраструктурного оверхеда (нет брокера, нет outbox, нет distributed-транзакций).
- Auth не зависит от Profiles.
- Profiles не зависит от Auth.

**Минусы:**

- Если пользователь сразу создаёт тренировку, Workouts делает синхронный вызов в Profiles. Если Profiles недоступен — `CreateWorkout` упадёт.
- Клиент обязан заполнить профиль **до** первой тренировки. Нельзя «попробовать без регистрации данных».
- Workouts получает `profile_completed` и сам решает, что делать. Profiles не знает про правила Workouts.

**Когда пересмотреть:**

- Если появится требование «профиль создаётся в момент регистрации» — переход на событие `user.registered` (Redis Streams / NATS).
- Если `GetProfile` станет горячим — кэш в Gateway или в Workouts.
