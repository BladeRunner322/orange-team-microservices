# ADR-003: Транзакции

## Контекст

В монолите транзакции использовались только там, где это было удобно. В частности, `recalculateScore` выполнял три действия подряд:

1. `UPDATE workouts SET workout_score = ...`
2. `UPDATE users SET user_workout_score = ...`
3. возврат

Без транзакции. При сбое между шагами 1 и 2 данные рассинхронизировались бы.

При распиле на микросервисы без специальных мер это превратилось бы в **распределённую транзакцию** между Workouts и Users — а её нельзя сделать обычным `BEGIN ... COMMIT`.

## Решение

- **Внутри одного сервиса** — обычные ACID-транзакции через `pkg/postgres.WithTx`. Пакет расширен методами `BeginTx` и `WithTx`.
- **Между сервисами** — distributed-транзакций **нет**.
- **Следствие ADR-002:** `user_workout_score` нигде не хранится, поэтому единственное место, куда пишет Workouts при изменении тренировки — собственная БД.
- **Cross-service операции** (например, `CreateWorkout` с профилем из Users) выполняются как **best-effort sync-вызовы**. Если Users недоступен — операция падает с ошибкой, пользователь повторяет. Компенсаций и саг нет.
- **Eventual consistency** через события — не используем на текущем этапе. Если понадобится в будущем (например, для Leaderboard), вводим осознанно отдельным ADR.

## Правила

1. Если операция пишет **в одну таблицу одной БД** — обычный `Exec`, транзакция не нужна.
2. Если операция пишет **в несколько таблиц одной БД** — обернуть в `WithTx`.
3. Если операция **читает из другой БД** — синхронный gRPC-вызов. Ошибку обрабатываем как обычно.
4. Если операция **пишет в другую БД** — сначала пересмотреть ADR-002 и подобные решения. Если всё же нужно — только через событие + идемпотентность.

## Последствия

**Плюсы:**

- Простая модель: транзакция = граница одного сервиса.
- Нет distributed-транзакций, нет саг, нет outbox.
- Легко рассуждать о консистентности.

**Минусы:**

- При падении одного сервиса во время sync-вызова операция не завершается (нужен ретрай клиента).
- Может потребоваться кэш, если sync-вызовы станут горячими.

**Когда пересмотреть:**

- Если появятся сценарии, требующие write в две БД атомарно — вводим событийную шину (Redis Streams / NATS) и outbox-pattern.
- Если потребуется eventual consistency для Leaderboard — отдельный ADR.
