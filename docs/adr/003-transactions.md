# ADR-003: Транзакции

## Контекст

В монолите транзакции использовались только там, где это было удобно. В частности, `recalculateScore` выполнял три действия подряд:

1. `UPDATE workouts SET workout_score = ...`
2. `UPDATE users SET user_workout_score = ...`
3. возврат

Без транзакции. При сбое между шагами 1 и 2 данные рассинхронизировались бы.

При распиле на микросервисы без специальных мер это превратилось бы в **распределённую транзакцию** между Workouts и Profiles — а её нельзя сделать обычным `BEGIN ... COMMIT`.

## Решение

- **Внутри одного сервиса** — ACID-транзакции в его PostgreSQL. Используем Avito Transaction Manager с драйвером pgx v5. Сценарий приложения задаёт границу транзакции через интерфейс `Do(ctx, fn)`. Менеджер открывает транзакцию, выполняет `fn` и делает commit или rollback. Репозиторий получает транзакцию из контекста callback, а вне транзакции использует пул. Менеджер и репозитории одного сервиса используют один пул и согласованные настройки контекста.
- **`pkg/postgres`** — `PgxPool` создаёт пул соединений pgx и хранит таймаут операций. Репозиторий вызывает `DefaultTrOrDB(ctx, db)`, чтобы получить транзакцию из контекста или использовать пул, и оборачивает выбранный исполнитель через `WithMappedErrors`. Правила преобразования ошибок находятся в `pkg/pgerrors`.
- **Статус** — миграция завершена. Exercises, Profiles, Habits и Workouts используют Avito Transaction Manager. Репозиторий Auth использует тот же способ выбора исполнителя SQL, а текущим сценариям Auth достаточно отдельных запросов. Самописные транзакционные обёртки удалены из `pkg/postgres`.
- **Между сервисами** — distributed-транзакций **нет**.
- **Следствие ADR-002:** `user_workout_score` нигде не хранится, поэтому единственное место, куда пишет Workouts при изменении тренировки — собственная БД.
- **Cross-service операции** (например, `CreateWorkout` с профилем из Profiles) выполняются как **best-effort sync-вызовы**. Если Profiles недоступен — операция падает с ошибкой, пользователь повторяет. Компенсаций и саг нет.
- **Eventual consistency** через события — не используем на текущем этапе. Если понадобится в будущем (например, для Leaderboard), вводим осознанно отдельным ADR.

## Правила

1. Для одного самостоятельного SQL-запроса достаточно транзакции, которую PostgreSQL открывает для самого запроса.
2. Если несколько SQL-запросов должны выполниться атомарно или держать блокировку до конца операции, обернуть их в `Do` и передавать контекст callback во все обращения к репозиториям. Например, в Exercises `SELECT … FOR UPDATE` и `UPDATE` одной таблицы выполняются вместе. В Workouts изменение упражнения и пересчёт балла тренировки выполняются в одной транзакции через два репозитория.
3. Если операция **читает из другой БД** — синхронный gRPC-вызов. Ошибку обрабатываем как обычно.
4. Если операция **пишет в другую БД** — сначала пересмотреть ADR-002 и подобные решения. Если всё же нужно — только через событие + идемпотентность.

## Последствия

**Плюсы:**

- Простая модель: транзакция = граница одного сервиса.
- Нет distributed-транзакций, нет саг, нет outbox.
- Легко рассуждать о консистентности.

**Минусы:**

- При падении одного сервиса во время sync-вызова операция не завершается (нужен ретрай клиента).
- Может потребоваться кэш, если sync-вызовы станут горячими.

**Когда пересмотреть:**

- Если появятся сценарии, требующие write в две БД атомарно — вводим событийную шину (Redis Streams / NATS) и outbox-pattern.
- Если потребуется eventual consistency для Leaderboard — отдельный ADR.
