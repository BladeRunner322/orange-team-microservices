# ADR-010: Общие инфраструктурные пакеты

## Контекст

Проект — монорепозиторий с несколькими сервисами (Auth, Gateway, Profiles, Exercises, в плане — Habits, Workouts, Leaderboard). Каждый сервис имеет свой `bootstrap.go`, `main.go`, HTTP-health-сервер, конфигурацию gRPC-сервера.

С ростом числа сервисов возникает вопрос: **что выносить в общие пакеты (`pkg/`), а что оставлять в каждом сервисе локально?**

Дублируется:
- Health/ready-эндпоинты — почти идентичны, разница только в имени сервиса и наборе проверок.
- Конструктор gRPC-сервера — одинаковый набор интерсепторов, TLS, reflection.
- Логика graceful shutdown — одинаковая.

Не дублируется, но похоже:
- `bootstrap.go` — общая структура, но разный набор зависимостей (Auth — JWT+Redis, Profiles — ничего специфичного, Workouts — клиенты к Profiles и Exercises).
- `main.go` — структура одна, детали разные (порты, имя сервиса).

Без чёткого правила одни и те же куски либо копипастятся бездумно, либо выносятся в «универсальный фреймворк», который сложнее, чем копипаста.

## Решение

Разделить инфраструктурный код на три категории.

### 1. Выносим в `pkg/` (общее)

**`pkg/health`** — health/ready/metrics-обработчики.

**Реализовано** (2026-10-05). Возвращает отдельные `http.HandlerFunc`,
чтобы каждый сервис вешал их на свой роутер (`ServeMux` в Auth/Profiles/Exercises,
chi в Gateway):

```go
mux.HandleFunc("/health", health.HealthHandler("auth"))
mux.HandleFunc("/ready", health.ReadyHandler(map[string]health.Check{
    "postgres": health.PostgresCheck(pool),
    "redis":    health.RedisCheck(redisClient),
}))
mux.Handle("/metrics", health.MetricsHandler())
```

Хелперы: `PostgresCheck(pool)`, `RedisCheck(client)`. Тип `Check func(ctx) error`.

**`pkg/grpc/server`** — конструктор gRPC-сервера с интерсепторами.

**Реализовано** (2026-10-05):

```go
s, err := grpcserver.New(grpcserver.Config{
    EnableTLS:        cfg.EnableTLS,
    TLSCertFile:      cfg.TLSCertFile,
    TLSKeyFile:       cfg.TLSKeyFile,
    EnableReflection: cfg.EnableReflection,
    WithUserID:       true, // false у Auth, true у Profiles/Exercises
    Logger:           log,
})
```

Внутри — стандартная цепочка: `Metrics → Recovery → [UserID] → Logging`, TLS-конфиг, reflection. `WithUserID` опционален: Auth — источник `user_id`, остальные — читают из metadata.

**Уже вынесено (для контекста):**
- `pkg/postgres`, `pkg/redis`, `pkg/ratelimit`
- `pkg/logger`, `pkg/metrics`
- `pkg/grpc/client`, `pkg/grpc/interceptors`
- `pkg/ctxkeys` — ключи контекста, которые пропагируются между сервисами через HTTP-заголовки и gRPC metadata (`user_id`, `role`, `request_id`)
- `pkg/nullable`

### 2. Не выносим (остаётся в сервисе)

**`bootstrap.go`** — оставить локальным.

Причины:
- Содержимое **разное** в каждом сервисе. У Auth — JWT manager + refresh repo, у Workouts — клиенты к Profiles и Exercises, у Leaderboard — что-то ещё.
- Попытка обобщить → **фреймворк** (fx, wire или собственный). Такой фреймворк сложнее для чтения и отладки, чем 170 строк копипасты.
- `bootstrap.go` читается за 2 минуты. С фреймворком — надо знать, как он устроен.

**`main.go`** — оставить локальным.

Причины:
- 60 строк, изменения — раз в полгода.
- Абстракция дороже выгоды.
- Разные порты, разные конфиги.

**`cmd/`, `config/`** — оставить локально. У каждого сервиса своя структура конфига.

**`Dockerfile`** — оставить локально (можно копипастить, но не выносить).

**Usecases, domain, repository** — очевидно, локально.

### 3. Серая зона — решать по мере появления

**Конфиг-парсер через `envconfig`** — оставить как есть (каждый сервис сам пишет `Config`, мало строк).

**Graceful shutdown** — пока оставить в `main.go`. Если сервисов станет 6+, можно вынести `pkg/shutdown`.

**Миграции** — остаются локальными, `migrate/migrate` в `docker-compose`.

## Правило для будущих решений

**Выносим, если:**
- Код **идентичен** в 3+ сервисах.
- Нет **разветвляющейся логики** (не «у Auth так, у Profiles иначе»).
- Абстракция **не требует** конфигурации сложнее, чем 2–3 параметра.
- Объём — **от 20 строк**. Мелочь не выносим.

**Не выносим, если:**
- Логика разная, но похожа по форме (bootstrap — разное содержимое).
- Абстракция становится **фреймворком** — надо изучать, как он работает.
- Копипаста **дешевле** по когнитивной нагрузке.
- В сервисе **один-два места**, где это используется.

## Порядок внедрения

**Реализовано** (2026-10-05).

Что сделано:

1. Создан `pkg/health` — отдельные `http.HandlerFunc` для `/health`, `/ready`, `/metrics`.
2. Создан `pkg/grpc/server` — конструктор gRPC-сервера с интерсепторами, TLS, reflection.
3. Мигрированы Auth, Profiles, Exercises, Gateway на новые пакеты.
4. Удалены локальные `health/`-пакеты из 4 сервисов.
5. Тесты и e2e — зелёные.

**Дальше:** для 5+ сервисов — пересмотреть правило. Если код снова начнёт дублироваться — вынести.

## Последствия

**Плюсы:**
- Меньше кода в каждом новом сервисе (~50 строк вместо 80+).
- Единообразие интерсепторов и health-эндпоинтов.
- Изменения в health/grpc-server — в одном месте.

**Минусы:**
- `pkg/health` и `pkg/grpc/server` — ещё два пакета, которые надо знать.
- При изменении контракта (например, новый обязательный интерсептор) — правки во всех сервисах одновременно.
- **Не** выносим bootstrap — значит, копипаста остаётся. Это осознанный выбор.

**Когда пересмотреть:**
- Если число сервисов превысит 8–10 — вероятно, потребуется более агрессивное вынесение (или переход на фреймворк типа fx).
- Если `bootstrap.go` начнёт дублироваться настолько, что изменения в одном надо вручную синхронизировать с другими — пересмотреть.
- Если появятся 3+ сервиса с идентичным `bootstrap` (сейчас такого нет).
