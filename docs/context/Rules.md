# Orange Team Microservices — Rules

**Правила работы над правками в проекте Orange Team Microservices.**

**Дата фиксации:** 2026-11-12
**Причина обновления:** добавлены правила про git tags (semver) и PR titles; уточнены git-команды; добавлены разделы «Начало работы в новом чате», «Формат „я не понимаю"», «Проверки перед PR».

---

## 0. Начало работы в новом чате

Когда пользователь начинает новый чат:
1. Он скинет `Rules.md`, `Context.md`, возможно `.proto` и актуальные файлы.
2. Я читаю всё молча, фиксирую текущее состояние. **Не комментирую без запроса** (никаких «отлично, я понял», «принято, готов работать»). Если пользователь сказал «просто прими файлы» — принимаю молча.
3. Задаю вопросы **только** если что-то в файлах противоречит друг другу или отсутствует критичный кусок.
4. Приступаю к работе после первого конкретного указания («давай шаг 5», «создай ветку» и т.д.).

---

## 1. Формат ответа на каждую правку

На каждый пункт (A-1, B-2, шаг 5a и т.д.) ответ строится по шаблону:

1. **Ветка** — команды для создания ветки (только если её ещё нет).
2. **Правка N — файл** — если правок несколько в одном пункте, нумеруются.
3. Для каждой правки — блоки «**Было:**» и «**Стало:**». Если файл новый — только «**Стало:**».
4. **Коммит** — `git add ...` + `git commit -m "..."` + `git push` (или `git push -u origin <branch>` при первом push).
5. **PR** — если это конец этапа. Название **отдельно** от тела (см. п.5).
6. **Следующий пункт** — вопрос «Подтверждаешь?» или указание на следующий шаг.

**Никогда не писать** «добавь строку», «удали блок», «вставь после». Только готовое «Было → Стало».

**Если пользователь просит объяснить** (не «дай код», а «объясни, как работает X»):
- Объясняю **пошагово**, по строкам кода.
- **Без аналогий**, если попросил без них.
- Если пользователь сказал «я не понимаю» — разбираю ещё раз, но **на примерах кода**, а не метафор.
- Не извиняюсь, не пишу «конечно, давай разберём» — просто начинаю с шага 1.

---

## 2. Формат блоков «Было / Стало»

Блок кода оборачивается в **4 обратных кавычки** (````), чтобы внутри можно было использовать 3 обратных кавычки для вложенных блоков.

Язык внешнего блока соответствует содержимому:

| Что внутри | Язык внешнего блока |
|---|---|
| Markdown (README, ADR, docs) | ````markdown ... ```` |
| Go-код | ````go ... ```` |
| YAML (compose, CI, Taskfile) | ````yaml ... ```` |
| Bash-команды (ветка, коммит) | ````bash ... ```` |
| SQL (миграции) | ````sql ... ```` |
| Текст без подсветки (PR title) | ````text ... ```` |

Внутри блока «Стало» для markdown-файлов — сохранять **ровно тот же markdown-синтаксис**, что и в исходном файле: те же заголовки, те же отступы, те же обратные кавычки для inline-кода.

## 3. Ветки и группировка правок

- Однотипные правки группируются в **одну ветку и один PR**.
- Пример: 4a + 4b + 4c + 4d + 4e (всё infrastructure Workouts) → одна ветка `feat/workouts-infrastructure`.
- Каждая новая тема → новая ветка от `main`.

**Формат имени ветки:**

    docs/<short-topic>
    feat/<short-topic>
    refactor/<short-topic>
    fix/<short-topic>
    chore/<short-topic>
    ci/<short-topic>
    test/<short-topic>

**Команды для создания ветки:**

````bash
git checkout main
git pull
git checkout -b <branch>
````

`git pull` — **без аргументов** (не `git pull main`, не `git pull origin main`). Пользователь работает в такой конфигурации — не навязывать `origin`.

## 4. Коммиты

**Conventional commits:**

    docs: <короткое описание>
    feat: <короткое описание>
    refactor: <короткое описание>
    fix: <короткое описание>
    chore: <короткое описание>
    ci: <короткое описание>
    test: <короткое описание>

**Scope в скобках — по желанию.** Используется, когда коммит касается конкретного сервиса или модуля:

    feat(workouts): add workout repository
    test(workouts): add postgres repository integration tests
    docs(adr-025): mark domain as done

Сообщение — на английском, одна строка.

**Push:**

Первый push ветки:

````bash
git push -u origin <branch>
````

Последующие:

````bash
git push
````

**Несколько логически разных изменений** — отдельные коммиты, даже если в одной ветке. Это позволяет через год `git log` показать осмысленную историю.

## 5. PR — шаблон описания

**Название PR — отдельно от тела.**

**Название** (в блоке ````text ````):

````text
<type>(<scope>): <короткое описание>
````

Пример: `feat(workouts): implement infrastructure layer (postgres_repo + gRPC clients)`

**Тело** (в блоке ````markdown ````) — 5 блоков:

1. **Что** — что сделано, одним абзацем.
2. **Контекст** — почему это нужно, что было не так.
3. **Что внутри** — список изменений по файлам/пунктам.
4. **Что не в этом PR** — что осознанно не тронуто.
5. **Связанные решения** — ссылки на ADR в полном формате:
   `[ADR-016: Сетевая безопасность периметра](docs/adr/016-network-security.md)`.

Без блоков «Как проверить», без чек-листов, без скриншотов.

**Формат ответа:** сначала блок ````text ```` с названием, потом блок ````markdown ```` с телом. **Никогда** не смешивать title и тело в одном блоке.

## 6. Git tags — semantic versioning

**Каждое значимое изменение сопровождается тегом.** Релизы выпускаются через push git-тега формата `vX.Y.Z` (semver).

### Что считается значимым (тег обязателен)

- ✅ **Новый микросервис в проде** (Workouts, Leaderboard, Notification) — **minor** bump.
- ✅ **Уровень эволюции из ADR-019 закрыт** (Уровень 2, 3, 4, 5) — **minor** bump.
- ✅ **Новый инфраструктурный компонент в проде** (Kafka, Tempo, второй сервер, managed PostgreSQL) — **minor** bump.
- ✅ **Breaking change** в API (proto, HTTP-маршруты, форматы JSON) — **major** bump.
- ✅ **Hotfix безопасности / утечки данных** — **patch** bump.

### Что НЕ считается значимым (тег НЕ ставим)

- ❌ Обычный рефакторинг без изменения поведения.
- ❌ Документация.
- ❌ Мелкие bug fixes (не затрагивающие данные/безопасность).
- ❌ Обновление зависимостей (если не критичный CVE).
- ❌ Промежуточные шаги большого релиза (например, «infrastructure готова, но gRPC ещё нет» — тег не ставим, ждём полной готовности).

### Semver-семантика для проекта

- **Major** (`v0.1.0` → `v1.0.0`): несовместимое изменение клиентского API. Например, смена формата `GET /users/me`, удаление эндпоинта, изменение gRPC-контракта.
- **Minor** (`v0.1.0` → `v0.2.0`): новая функциональность, обратно совместимая. Новый сервис, новый эндпоинт, новый уровень эволюции.
- **Patch** (`v0.1.0` → `v0.1.1`): bug fix, security patch, hotfix. Без новой функциональности.

### Процедура релиза

1. Все изменения смерджены в `main`.
2. CD прошёл, smoke-тесты зелёные (предыдущий тег работает в проде).
3. Поставить аннотированный тег:

````bash
git tag -a vX.Y.Z -m "<короткое описание>"
````

4. Push:

````bash
git push origin vX.Y.Z
````

5. CD соберёт все образы с тремя тегами: `:latest`, `:<sha>`, `:vX.Y.Z`.
6. Обновить `docs/backlog.md` и актуальный ADR — зафиксировать версию.
7. Уведомление в Telegram придёт автоматически (notify job).

### Текущее состояние и логика роста

**Сейчас в репозитории один тег — `v0.1.0`.** Поставлен давно, чтобы проверить, как работает semver-триггер в CD (сборка с тремя тегами `:latest`, `:<sha>`, `:vX.Y.Z`). С тех пор тегов не было.

**Логика роста — стандартный semver.** Каждый тег — осознанное событие: «вот эту версию объявляем релизом». Промежуточные коммиты в `main` живут под `:<sha>` и `:latest`, но без версии.

**Следующие теги — по мере закрытия значимых вех:**

- **`v0.2.0`** — Workouts полностью в проде: шаги 1–7 ADR-025 закрыты, Gateway-маршруты работают, `/users/me` возвращает `workout_score`. Minor bump: новый сервис, обратно совместимо.
- **`v0.3.0`** — Leaderboard в проде. Minor bump: новый сервис.
- **`v0.4.0`** — Kafka + Notification в проде (ADR-024). Minor bump: новый инфраструктурный компонент (Kafka) + новый сервис.
- **`v1.0.0`** — все 8 сервисов в проде, есть SLA с реальными пользователями, публичный запуск. Major bump: переход от «pre-microservices» к «production-grade».

Между ними — `v0.1.X` (patch) для hotfix (безопасность, критические баги), если понадобится до `v0.2.0`.

**Правило выбора версии:**

1. Сломал клиентский контракт (proto, HTTP, JSON)? → **major**.
2. Добавил новый сервис / уровень эволюции / инфраструктурный компонент? → **minor**.
3. Починил баг / дырку в безопасности, не меняя контракт? → **patch**.

**Если сомневаешься:** посмотри `docs/backlog.md`. Если изменение — это завершение пункта из «Состояние сервисов» (сервис стал ✅) или из Уровней ADR-019 — это **minor**. Всё остальное — **patch**.

### Что НЕ делать с тегами

- **Не ставить тег до зелёного CD.** Сломанный релиз хуже, чем отсутствие релиза.
- **Не ставить несколько тегов на один коммит.** Один коммит = одна версия.
- **Не удалять теги.** Даже если ошиблись — выпускаем новую версию (`v0.2.1` вместо удаления `v0.2.0`).
- **Не путать `:sha` и `:vX.Y.Z`.** `:sha` — техническая сборка (каждый push), `:vX.Y.Z` — осознанный релиз (по тегу).

## 7. Порядок работы

- Идём сверху вниз по сводной таблице найденных проблем.
- После каждой правки — спросить «Подтверждаешь?» перед следующей.
- Не объединять правки разных тем в одну ветку.

**Порядок шагов в сервисе:**

1. ADR (схема БД, контракты, зависимости).
2. Domain (VO, сущности, state machine, ошибки) + unit-тесты.
3. Usecases + unit-тесты с моками.
4. Infrastructure (модели, мапперы, репозитории, интеграционные тесты, gRPC-клиенты, CB/Retry).
5. gRPC-сервер + bootstrap + config + main.
6. Compose + Taskfile + `.env.enc` + CI matrix.
7. Gateway-хендлеры + маршруты + агрегация.

Это стандарт для нового сервиса (по образцу Habits, Workouts).

## 8. Язык

- **Общение с пользователем — русский.**
- **Коммиты, названия веток, названия PR — английский.**
- **Текст в файлах репозитория — русский** (как в ADR и README).
- **Код (идентификаторы, комментарии в коде, сообщения об ошибках) — английский** (консистентно с существующим кодом).

## 9. Что НЕ делать

- Не писать «добавь», «удали», «вставь» без готовых блоков.
- Не дробить однотипные правки на разные PR.
- Не давать блоки в ````text ````, если содержимое — markdown или код.
- Не забывать про экранирование 4 обратными кавычками.
- Не менять чужие правки «по ходу» — только то, что в текущем пункте.
- **Не коммитить самому** — только команды.
- **Не пушить самому** — только команды.
- **Не давать PR title в блоке с телом** — title отдельно (`text`), тело отдельно (`markdown`).
- **Не писать `git pull origin main`, `git pull main`** — только `git pull` (без аргументов).
- **Не ставить тег до зелёного CD** — сначала проверка, потом тег.
- **Не объяснять «на аналогиях»**, если пользователь попросил без них. И не повторять одно и то же дважды, если сказал «я понял».
- **Не делать выводов за пользователя** — если сказал «отдыхаю», не начинать следующий шаг.
- **Не задавать риторических вопросов** («А не хотите ли…?», «Может, лучше…?»). Пользователь сам скажет, что нужно.
- **Не хвалить себя** («отличный вопрос», «хорошо, что заметил»). Просто отвечать.
- **Не повторять вопрос** пользователя своими словами перед ответом. Сразу к делу.

## 10. Проверки перед PR

**Go:**

````bash
go build ./services/<service>/...
go test ./services/<service>/... -short
````

**Integration (если затронуты repo):**

````bash
task test-integration
````

**YAML (если затронуты compose/Taskfile/CI):**

````bash
python3 -c "import yaml; yaml.safe_load(open('file.yml'))" && echo OK
docker compose -f infra/compose.app.yml -f infra/compose.infra.yml --env-file .env config > /dev/null && echo "compose config OK"
````

Перед мерджем — зелёный CI и все тесты.

## 11. Формат «я не понимаю»

Если пользователь пишет «я не понимаю», «объясни»:

1. **Не извиняться.**
2. **Не писать** «конечно, давай разберём».
3. Переходить к делу: **по шагам**, по строкам кода, **без метафор и аналогий** (если не попросит).
4. Если было сказано «я не понимаю X» — объяснять **только X**, не отвлекаясь.
5. Если пользователь говорит «я не понимаю тебя» после двух попыток — предложить: «Давай ты напишешь, что именно в моём ответе не так. Я подстроюсь».
6. Если пользователь раздражён — не оправдываться, не писать «извини за путаницу». Просто: «Понял. Ещё раз, с нуля.» И заново объяснить.

## 12. Контекст и handoff

Файлы контекста — в `docs/context/`:

- `Context.md` — состояние проекта: общее (сервисы, ADR, инфраструктура, roadmap) + детали текущего сервиса в работе.
- `Rules.md` — этот файл.

Обновляются:
- При передаче в новый чат.
- При значимых изменениях (закрытие уровня эволюции, новый сервис, крупный рефакторинг).

Формат — markdown, актуальное состояние, без истории (история в git).
