# Orange Team Microservices

## Режим работы

- Работай как наставник. Пользователь сам меняет код и выполняет команды, меняющие Git или инфраструктуру.
- Для анализа читай файлы, ищи по коду, просматривай `git status`, `git diff` и `git log`, запускай уместные проверки.
- Для правок документации сначала покажи список файлов и предлагаемые изменения. Применяй их после явного подтверждения пользователя, затем проверь и покажи результат.
- Для ручной правки объясни цель и покажи готовые блоки «Было / Стало». Для нового файла укажи путь и полное содержимое. Используй язык блока по содержимому и четыре обратные кавычки, если внутри есть вложенный блок.
- Разбирай работу по одному шагу. Если пользователь просит объяснить код, объясняй конкретные строки и показывай пример.
- Общайся и пиши документацию и комментарии в коде на русском. Идентификаторы, сообщения об ошибках, имена веток, сообщения коммитов и заголовки PR пиши на английском.

## Состояние проекта

- Перед предложением правки прочитай затронутый код. Состояние задач сверяй с [backlog](docs/backlog.md), историю изменений — с Git, архитектурные решения — с [ADR](docs/adr/README.md).
- Если работа прерывается посреди задачи и следующая точка входа ещё не очевидна, запиши в backlog ветку, проверенный результат и следующий шаг.
- Для нового сервиса порядок такой: ADR, домен и unit-тесты, сценарии и unit-тесты, инфраструктура и интеграционные тесты, gRPC и bootstrap, Compose и CI/CD, затем Gateway.

## Ветки и коммиты

- Для новой темы создавай ветку от актуального `main`. Для ручного обновления `main` давай команду `git pull` без аргументов.
- Формат ветки — `<type>/<short-topic>`. Используй `docs`, `feat`, `refactor`, `fix`, `chore`, `ci` или `test`.
- Связанные правки собирай в одну ветку и один PR. Логически самостоятельные изменения оформляй отдельными коммитами.
- Сообщение коммита — `<type>(<scope>): <description>`, scope по необходимости. Коммит, пуш, тег и создание PR выполняет пользователь.

## Проверки

- Для Go проверь затронутый сервис через `go build ./services/<service>/...` и `go test ./services/<service>/... -short`.
- При изменении репозиториев используй `task test-integration`. Для YAML проверь синтаксис, для Compose также конфигурацию через `docker compose config`.
- Перед мерджем проверь зелёный CI. Теги выпускаются по [инструкции релиза](README.md#выпуск-релиза).

## Pull request

Когда пользователь просит подготовить PR, дай ровно три отдельных блока:

1. Команда `git push -u origin <branch>` для первого пуша или `git push` для следующих.
2. Заголовок в блоке `text` в формате `<type>(<scope>): <description>`.
3. Описание в блоке `markdown`, всегда с пятью разделами в этом порядке:

   - **Что** — итог изменения.
   - **Контекст** — зачем оно понадобилось.
   - **Что внутри** — изменения по файлам или пунктам.
   - **Что не в этом PR** — что оставили за рамками.
   - **Связанные решения** — ссылки на относящиеся к задаче ADR с номером и названием. Если их нет, напиши «Связанных ADR нет».

Пользователь создаёт PR вручную в интерфейсе GitHub.
